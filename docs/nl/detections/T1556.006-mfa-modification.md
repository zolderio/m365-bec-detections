# T1556.006 — Modify Authentication Process: Multi-Factor Authentication

| | |
|---|---|
| **Naam in het advies** | Modify Authentication Process — het toevoegen van een eigen MFA-methode aan het account van het slachtoffer |
| **Naam in MITRE ATT&CK** | Modify Authentication Process: Multi-Factor Authentication |
| **MITRE-tactiek** | Persistence (TA0003), Credential Access (TA0006), Defense Impairment (TA0112, in oudere versies Defense Evasion) |
| **Whitepaper-maatregel** | 009 — OAuth-app consent beperken of uitschakelen (prioriteit Hoog) |
| **Verwante techniek** | [T1098.001](T1098.001-additional-cloud-credentials.md) — dezelfde maatregel, de app-kant |
| **Status van deze detectie** | KQL niet uitgevoerd tegen een productie-tenant — zie [teststatus](../teststatus.md) |

## Aanbeveling

> ### `SENTINEL-RULE` — bouw hier een eigen analytic rule
>
> Hier is geen alert. Niet in Purview — er is geen default alert policy voor
> security info — en niet in Entra ID Protection: in de gedocumenteerde lijst
> met risicodetecties staat geen enkele detectie op het registreren, verwijderen
> of degraderen van een MFA-methode. De naastgelegen detectie
> `Suspicious MFA authentication approval` gaat over het góédkeuren van een
> prompt, niet over het registreren van een methode, en vereist bovendien
> Microsoft Entra ID P2. De gebeurtenissen staan wél volledig in de
> Entra-auditlog en zijn goedkoop te alarmeren. Dit is de detectie met de beste
> verhouding tussen moeite en opbrengst in dit hele cluster: bouw hem, scope
> hem niet te smal, en koppel hem aan de voorafgaande sign-in.

## Is er een Defender-alert voor?

**Nee.**

| | |
|---|---|
| **Purview alert policy** | Geen. De categorieën *Threat management*, *Permissions*, *Mail flow* en *Information governance* bevatten geen policy die security info-registratie volgt. |
| **Entra ID Protection** | Geen risicodetectie voor het registreren, wijzigen of verwijderen van een authenticatiemethode. |
| **Defender for Cloud Apps** | Geen anomaly detection policy voor deze handeling. |
| **Wat er in de buurt komt** | `Suspicious MFA authentication approval` (sign-in risk, real-time, riskEventType `authenticatorPhishing`, **Microsoft Entra ID P2**) en `User reported suspicious activity` (user risk, offline, riskEventType `userReportedSuspiciousActivity`, **P2**, en alleen als *Report suspicious activity* aan staat). Beide gaan over de MFA-prompt, niet over de registratie. |

Zonder Entra ID P2 zie je van de premium-detecties alleen
**`Additional risk detected`** zonder details; de risk detections-rapportage is
in P1 *"Limited Information. No details drawer."* en in Free helemaal afwezig.

De alert moet je dus zelf bouwen. De goede kant van dat verhaal: de
auditactiviteiten zijn stabiel en exact gedocumenteerd.

## De auditactiviteiten (exact)

Alle zes staan in de Entra-auditreferentie onder categorie **UserManagement**,
service **Authentication Methods**:

| Activiteit | Wat het betekent |
|---|---|
| `User registered security info` | De gebruiker heeft zelf een methode toegevoegd. Dit is het kernevent. |
| `User deleted security info` | Een methode is verwijderd. Aanvallers gebruiken dit om de echte gebruiker buiten te sluiten of om een sterke methode weg te halen. |
| `User changed default security info` | De standaardmethode is verlegd, bijvoorbeeld van FIDO2 naar SMS. Degradatie zonder dat er iets is verwijderd. |
| `User started security info registration` | De aanloop. Nuttig als vroeg signaal en om afgebroken pogingen te zien. |
| `User canceled security info registration` | Afgebroken registratie. |
| `Admin registered security info` / `Admin deleted security info` / `Admin updated security info` | Dezelfde handelingen door een beheerder — bij een gecompromitteerd beheeraccount de zwaarste variant. |

## Benodigde databron

| Platform | Tabel | Wat er onboard moet zijn |
|---|---|---|
| Microsoft Sentinel | `AuditLogs` | Data connector **Microsoft Entra ID**, logcategorie **AuditLogs** aangevinkt in de diagnostic setting van Entra ID. |
| Microsoft Sentinel | `SigninLogs` | Zelfde connector, logcategorie **SignInLogs** apart aanvinken. Nodig voor de correlatie hieronder. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps met de Microsoft 365-connector. **Zie de waarschuwing hieronder.** |

Deze detectie hangt **niet** aan maatregel 012 (Unified Audit Log): de
Entra-auditlog gaat via diagnostic settings, niet via de UAL.

**Niet geverifieerd:** dat de security info-activiteiten in `CloudAppEvents`
terechtkomen. Vastgesteld is dát Entra-auditevents in die tabel landen onder
`Application == "Office 365"` — Microsofts eigen hunting-query voor
`Consent to application.` bewijst dat. Of de UserManagement-activiteiten rond
security info daar ook bij zitten, kon niet uit de Microsoft-documentatie worden
bevestigd. De betrouwbare route is `AuditLogs` in Sentinel. Wil je het toch in
Defender XDR proberen, begin dan met de inventarisatiequery onderaan.

## KQL — Sentinel (AuditLogs): MFA-methode geregistreerd, verwijderd of gedegradeerd

<!-- query
platform: sentinel
name: MFA method registered, deleted or changed
technique: T1556.006
severity: Medium
tactics: [Persistence, DefenseEvasion]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// De kernregel. Bewust breed: alle mutaties op security info, ook de
// admin-varianten. Het volume hiervan is in de meeste tenants laag genoeg om
// er een alert op te zetten zonder tuning.
let lookback = 1d;
AuditLogs
| where TimeGenerated > ago(lookback)
| where Category == "UserManagement"
| where OperationName in (
    "User registered security info",
    "User deleted security info",
    "User changed default security info",
    "Admin registered security info",
    "Admin deleted security info",
    "Admin updated security info")
| where Result == "success"
| extend Actor              = tostring(InitiatedBy.user.userPrincipalName)
| extend ActorIP            = tostring(InitiatedBy.user.ipAddress)
| extend TargetUser         = tostring(TargetResources[0].userPrincipalName)
// Het type methode (Microsoft Authenticator, SMS, telefoon, FIDO2) staat in de
// vrije tekst van AdditionalDetails; de sleutelnaam verschilt per activiteit,
// dus hier bewust niet hard uitgeparsed maar meegegeven ter beoordeling.
| extend Details            = tostring(AdditionalDetails)
| extend AdminActionOnOther = tolower(Actor) != tolower(TargetUser)
| project TimeGenerated, OperationName, Actor, ActorIP, TargetUser,
          AdminActionOnOther, Details, CorrelationId
| order by TimeGenerated desc
```

## KQL — Sentinel: registratie kort na een sign-in vanaf een nieuw IP

<!-- query
platform: sentinel
name: MFA method registered within an hour of a sign-in from an unseen IP address
technique: T1556.006
severity: High
tactics: [Persistence, CredentialAccess]
interval: P1D
lookback: P14D
parameters: []
deployable: true
-->
```kql
// Dit is de regel die je écht wilt hebben. Een MFA-registratie op zichzelf is
// alledaags (nieuwe telefoon). Een MFA-registratie binnen een uur na een
// geslaagde sign-in vanaf een IP-adres dat deze gebruiker de afgelopen 30 dagen
// nog nooit gebruikte, is het AiTM-patroon.
let baseline = 30d;
let window   = 1h;
let recent   = 7d;
let knownIPs =
    SigninLogs
    | where TimeGenerated between (ago(baseline) .. ago(recent))
    | where ResultType == "0"
    | distinct UserPrincipalName, IPAddress;
let newSignIns =
    SigninLogs
    | where TimeGenerated > ago(recent)
    | where ResultType == "0"
    | join kind=leftanti knownIPs on UserPrincipalName, IPAddress
    | project SignInTime = TimeGenerated, UserPrincipalName, IPAddress,
              Country = tostring(LocationDetails.countryOrRegion),
              AppDisplayName, UserAgent;
AuditLogs
| where TimeGenerated > ago(recent)
| where Category == "UserManagement"
| where OperationName in ("User registered security info",
                          "User deleted security info",
                          "User changed default security info")
| where Result == "success"
| extend UserPrincipalName = tostring(InitiatedBy.user.userPrincipalName)
| join kind=inner newSignIns on UserPrincipalName
| where TimeGenerated between (SignInTime .. SignInTime + window)
| project RegistrationTime = TimeGenerated, OperationName, UserPrincipalName,
          SignInTime, IPAddress, Country, AppDisplayName, UserAgent
| order by RegistrationTime desc
```

## KQL — Sentinel: sterke methode weg, zwakke methode erbij

<!-- query
platform: sentinel
name: MFA method removed and a new one registered within 24 hours
technique: T1556.006
severity: Medium
tactics: [Persistence, DefenseEvasion]
interval: P1D
lookback: P14D
parameters: []
deployable: true
-->
```kql
// Degradatie binnen 24 uur: eerst iets verwijderen of de default verleggen, dan
// iets nieuws registreren. Bij een echte telefoonwissel gebeurt dit ook, dus
// dit is een prioriteringsregel en geen bewijs.
let window = 24h;
let changes =
    AuditLogs
    | where TimeGenerated > ago(14d)
    | where Category == "UserManagement"
    | where OperationName has "security info"
    | where Result == "success"
    | extend User = tostring(InitiatedBy.user.userPrincipalName)
    | extend IP = tostring(InitiatedBy.user.ipAddress);
changes
| where OperationName in ("User deleted security info", "User changed default security info")
| project DeleteTime = TimeGenerated, User, DeleteIP = IP, FirstAction = OperationName
| join kind=inner (
    changes
    | where OperationName == "User registered security info"
    | project RegistrationTime = TimeGenerated, User, RegistrationIP = IP
  ) on User
| where RegistrationTime between (DeleteTime .. DeleteTime + window)
| project User, FirstAction, DeleteTime, DeleteIP, RegistrationTime, RegistrationIP
| order by RegistrationTime desc
```

## KQL — Defender XDR advanced hunting (CloudAppEvents), met voorbehoud

<!-- query
platform: defender-xdr
name: Inventory of security info action types in the cloud app audit trail
technique: T1556.006
severity: Informational
tactics: [Persistence]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// Eerst vaststellen óf de activiteiten in jouw tenant in deze tabel zitten.
// Draai deze inventarisatie voordat je op de tweede query bouwt.
CloudAppEvents
| where Timestamp > ago(7d)
| where Application == "Office 365"
| where ActionType has "security info"
| distinct ActionType
```

<!-- query
platform: defender-xdr
name: Security info changes in the cloud app audit trail
technique: T1556.006
severity: Medium
tactics: [Persistence]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// Als de vorige query resultaten geeft, is dit de detectie.
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Office 365"
| where ActionType has "security info"
| project Timestamp, ActionType, AccountDisplayName, AccountObjectId, IPAddress,
          CountryCode, City, Isp, UserAgent, IsAdminOperation, RawEventData
| order by Timestamp desc
```

## Waarom dit BEC is

Het registreren van een eigen MFA-methode is de goedkoopste persistentie die er
is: geen malware, geen app, geen code — alleen de portal *My Sign-Ins* waar de
gecompromitteerde gebruiker zelf toegang toe heeft. Het overleeft een
wachtwoordreset, en het maakt van een gestolen sessietoken een permanente
toegang.

MITRE noemt bij T1556.006 als expliciet procedurevoorbeeld **Scattered Spider**,
dat *"registers their own MFA tokens after account compromise"*, en bij
[T1098.001](T1098.001-additional-cloud-credentials.md) **Storm-0501**, dat
administratorwachtwoorden zonder MFA reset en daarna een eigen MFA-methode
registreert.

Expel beschrijft de handeling in de AiTM/BEC-context en wijst dezelfde
auditgebeurtenis aan: *"Attackers will register their own MFA devices as a form
of persistence. Why? Their session token won't be valid forever."* — en als
detectie: *"look for the 'User registered security info' event to detect when a
user registers a new MFA method."*

Dit is ook de reden dat maatregel 004 (phishing-resistente MFA) alleen werkt als
je maatregel 009 erbij monitort: een aanvaller die zijn eigen Authenticator mag
registreren, heeft de FIDO2-sleutel van het slachtoffer niet nodig.
