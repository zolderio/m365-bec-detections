## Aanbeveling

> ### `SENTINEL-RULE` — bouw hier een eigen analytic rule
>
> Er bestaat geen enkele standaard alert policy voor aanmeldingen: het complete
> overzicht van alert policies in het Defender-portaal gaat over mail,
> bestanden, formulieren en beheerhandelingen, niet over sign-ins. De detectie
> die het advies onder maatregel 007 vraagt zit volledig in Microsoft Entra ID
> Protection, en de detecties die er inhoudelijk toe doen — *Atypical travel*,
> *Malicious IP address*, *Unfamiliar sign-in properties*, *Verified threat
> actor IP* — vereisen zonder uitzondering **Microsoft Entra ID P2**. Zonder P2
> krijg je `Additional risk detected` zonder details, en daar kun je niets mee.
> De sign-in logs zelf heb je met P1 al; daar bouw je de rules op. Heb je P2,
> zet dan bovendien een risicogebaseerd Conditional Access-beleid aan — dat is
> geen detectie maar de blokkade die maatregel 006 bedoelt.

## Is er een Defender-alert voor?

**Nee, geen alert policy. Wel Entra ID Protection, en dat is premium.**

De relevante sign-in risk detections, met het licentieniveau zoals Microsoft dat
per detectie documenteert:

| Risk detection | `riskEventType` | Type | Licentie |
|---|---|---|---|
| `Anonymous IP address` | `anonymizedIPAddress` | Real-time | **Entra ID Free of P1** |
| `Microsoft Entra threat intelligence (sign-in)` | `investigationsThreatIntelligence` | Real-time of offline | **Entra ID Free of P1** |
| `Atypical travel` | `unlikelyTravel` | Offline | **Entra ID P2** |
| `Malicious IP address` | `maliciousIPAddress` | Offline | **Entra ID P2** |
| `Unfamiliar sign-in properties` | `unfamiliarFeatures` | Real-time | **Entra ID P2** |
| `Verified threat actor IP` | `nationStateIP` | Real-time | **Entra ID P2** |
| `Suspicious browser` | `suspiciousBrowser` | Offline | **Entra ID P2** |
| `Impossible travel` | `mcasImpossibleTravel` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, óf **M365 E5 met EMS E5** |
| `New country` | `newCountry` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, óf **M365 E5 met EMS E5** |
| `Activity from anonymous IP address` | `riskyIPAddress` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, óf **M365 E5 met EMS E5** |
| `Leaked credentials` | `leakedCredentials` | Offline | **Entra ID Free of P1** (vereist password hash synchronization voor on-premises wachtwoorden) |

Bron: https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks

Twee opmerkingen die er in de praktijk toe doen:

- **`Atypical travel` en `Impossible travel` zijn niet hetzelfde.** De eerste is
  een Entra-detectie op sign-ins, de tweede komt uit Defender for Cloud Apps en
  kijkt naar *activiteiten*. Ze hebben verschillende licenties en verschillende
  false positives. Noem ze niet door elkaar in een runbook.
- **Deze detecties gelden niet op mislukte of niet-interactieve aanmeldingen.**
  Microsoft: *"Impossible travel, activity from infrequent countries/regions,
  activity from anonymous IP addresses, and activity from suspicious IP
  addresses alerts don't apply on failed logins and non-interactive logins."*
  Juist bij tokenreplay is de aanmelding niet-interactief.

**Vervallen, niet meer op bouwen.** De Defender for Cloud Apps-policies
`Activity from anonymous IP addresses` en `Activity from suspicious IP addresses`
zijn per juni 2025 als legacy policy uitgezet en gemigreerd naar het dynamische
model, onder respectievelijk `Activity from a TOR IP address` /
`Anonymous proxy activity` en `Successful logon from a suspicious IP address` /
`Activity from a password-spray associated IP address`. De gelijknamige
Entra-detectie `Activity from anonymous IP address` bestaat wél nog.
Bron: https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

**Maatregel 006 is een licentiefeit, geen open punt.** Conditional Access
vereist **Microsoft Entra ID P1**; Microsoft 365 Business Premium bevat het ook.
Risicogebaseerde Conditional Access (sign-in risk en user risk) vereist
**Entra ID P2**. Zonder P2 kun je de eerste drie punten van de effectieve aanpak
in het advies wél uitvoeren (MFA afdwingen, landen blokkeren,
apparaatcompliance) en het vierde (risicogebaseerd blokkeren) niet.
Bron: https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview

## Benodigde databron

| Platform | Tabel | Wat er onboard moet zijn |
|---|---|---|
| Microsoft Sentinel | `SigninLogs`, `AADNonInteractiveUserSignInLogs` | Data connector **Microsoft Entra ID**. Microsoft: *"A Microsoft Entra ID P1 or P2 license is required to ingest sign-in logs into Microsoft Sentinel."* |
| Microsoft Sentinel | `AADUserRiskEvents`, `AADRiskyUsers` | Zelfde connector (log types *User risk events* en *Risky users*). Detectiedetails vereisen P2. |
| Microsoft Sentinel | `AuditLogs` | Zelfde connector. Nodig om te zien wat het account ná de aanmelding in de directory deed. |
| Microsoft Sentinel | `OfficeActivity` | Data connector **Microsoft 365** (Exchange-workload). Vereist een ingeschakelde Unified Audit Log — **maatregel 012**. |
| Defender XDR advanced hunting | `EntraIdSignInEvents` | **Entra ID P2**. Vervangt `AADSignInEventsBeta` per **19 oktober 2026**. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps gekoppeld (*Settings > Cloud apps > App connectors*, met *Microsoft 365 activities* aan). Ook hier geldt maatregel 012 voor de Exchange-activiteiten. |

Eén tabel die je hier **niet** moet gebruiken: `IdentityLogonEvents` bevat
authenticaties uit on-premises Active Directory (Defender for Identity) plus de
Entra-aanmeldingen die Defender for Cloud Apps ziet — en Microsoft tekent daarbij
aan dat dat *"specifically interactive sign-ins and authentication activities
using ActiveSync and other legacy protocols"* zijn. Niet-interactieve
aanmeldingen ontbreken. Voor cloud-sign-ins is `EntraIdSignInEvents` of
`SigninLogs` de juiste bron.

## KQL — Sentinel: geslaagde aanmelding met risico dat niet is geblokkeerd

```kql
// De kern van maatregel 006 + 007 samen: Entra zág risico, en de aanmelding
// slaagde toch. Dat is óf een gat in het Conditional Access-beleid, óf een
// policy in report-only. Beide zijn een bevinding.
let lookback = 7d;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"
| where RiskLevelDuringSignIn in ("medium", "high")   // 'hidden' = geen P2, laat die weg
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AutonomousSystemNumber,
          AppDisplayName, ClientAppUsed, UserAgent,
          RiskLevelDuringSignIn, RiskEventTypes_V2, RiskState, RiskDetail,
          AuthenticationRequirement, ConditionalAccessStatus, SessionId
| order by TimeGenerated desc
```

`RiskLevelDuringSignIn` kent de waarde `hidden`, en die betekent volgens
Microsoft dat de gebruiker of de aanmelding niet onder ID Protection viel — dus
geen P2. Zie je alleen `hidden`, dan is er niets kapot aan je query; dan is er
geen licentie.

## KQL — Sentinel: nieuw land voor deze gebruiker (werkt zonder P2)

```kql
// Zelfbouw-alternatief voor 'New country', dat P2 + Defender for Cloud Apps
// vereist. Baseline van 30 dagen, en dan alles wat daarbuiten valt. Bewust op
// land en niet op stad: geolocatie op stadsniveau is te onbetrouwbaar om een
// alert op te bouwen.
let lookback  = 1d;
let baselineVan = 31d;
let baseline =
    SigninLogs
    | where TimeGenerated between (ago(baselineVan) .. ago(lookback))
    | where ResultType == "0"
    | summarize BekendeLanden = make_set(Location, 50) by UserPrincipalName;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"
| join kind=leftouter baseline on UserPrincipalName
| where isnotempty(Location)
| where isempty(BekendeLanden) or not(set_has_element(BekendeLanden, Location))
| project TimeGenerated, UserPrincipalName, Location, IPAddress, AutonomousSystemNumber,
          AppDisplayName, ClientAppUsed, AuthenticationRequirement,
          ConditionalAccessStatus, BekendeLanden
| order by TimeGenerated desc
```

Sluit vakantieperiodes en bekende reizigers uit met een watchlist; anders is
deze rule in september onbruikbaar.

## KQL — Sentinel: de risicodetecties zelf uitlezen

```kql
// Alle ID Protection-detecties op één rij, inclusief de detecties die zonder P2
// als 'Additional risk detected' binnenkomen (riskEventType 'generic').
AADUserRiskEvents
| where TimeGenerated > ago(30d)
| project TimeGenerated, ActivityDateTime, UserPrincipalName, RiskEventType,
          RiskLevel, RiskState, RiskDetail, DetectionTimingType, Activity,
          IpAddress, Location, Source, TokenIssuerType, CorrelationId
| order by TimeGenerated desc
```

```kql
// En de tegenvraag die er in een BEC-onderzoek écht toe doet: is er na de
// risicovolle aanmelding iets in de mailbox gebeurd? OfficeActivity vereist
// maatregel 012 (UAL aan).
let risico =
    AADUserRiskEvents
    | where TimeGenerated > ago(7d)
    | where RiskLevel in ("medium", "high")
    | project RisicoOp = TimeGenerated, UserPrincipalName, RiskEventType, IpAddress;
OfficeActivity
| where TimeGenerated > ago(7d)
| where Operation in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules",
                       "Add-MailboxPermission", "Set-Mailbox")
| join kind=inner risico on $left.UserId == $right.UserPrincipalName
| where TimeGenerated between (RisicoOp .. RisicoOp + 24h)
| project TimeGenerated, RisicoOp, UserId, RiskEventType, Operation, ClientIP, Parameters
| order by TimeGenerated desc
```

## KQL — Defender XDR advanced hunting (EntraIdSignInEvents)

```kql
// Geslaagde aanmelding met een risiconiveau tijdens de aanmelding. De schaal is
// hier numeriek: 0 (niet gezet), 1 (none), 10 (low), 50 (medium), 100 (high).
EntraIdSignInEvents
| where Timestamp > ago(7d)
| where ErrorCode == 0
| where RiskLevelDuringSignIn >= 50            // medium en high
| project Timestamp, AccountUpn, AccountObjectId, IPAddress, Country, City,
          Application, ClientAppUsed, UserAgent, RiskLevelDuringSignIn,
          RiskEventTypes, RiskState, AuthenticationRequirement,
          ConditionalAccessStatus, IsCompliant, IsManaged, SessionId
| order by Timestamp desc
```

`IsCompliant` en `IsManaged` staan in de output omdat maatregel 006 er expliciet
om vraagt: een geslaagde risicovolle aanmelding vanaf een onbeheerd apparaat is
een ander verhaal dan dezelfde aanmelding vanaf een compliant laptop.

## Waarom dit BEC is

Een geldig account is bij BEC geen tussenstap maar het hele doel: er wordt niets
geïnstalleerd, niets geëxploiteerd, en er is dus ook geen malware om te vinden.
FBI, CISA, NSA, CSE, AFP en ASD's ACSC beschrijven in advisory **AA24-290A**
(16 oktober 2024) hoe actoren *"valid user and group email accounts"* [T1078]
gebruiken om toegang te krijgen tot **Microsoft 365 en Azure** [T1078.004], en
die toegang vervolgens op criminele fora verkopen aan partijen die er verder mee
gaan. Microsoft heeft er in Defender XDR een eigen incidentcategorie voor: bij
hoge zekerheid wordt aan de titel *(attack disruption)* toegevoegd, met als
voorbeeld in de documentatie letterlijk *"BEC financial fraud attack launched
from a compromised account (attack disruption)"*.
