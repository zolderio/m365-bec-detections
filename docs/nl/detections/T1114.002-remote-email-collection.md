# T1114.002 — Remote Email Collection

| | |
|---|---|
| **MITRE-tactiek** | Collection |
| **Whitepaper-maatregel** | 016 — Blokkering van automatische e-mailforwarding (prioriteit Hoog)<br>017 — Teams & SharePoint-collaboration beperken (prioriteit Midden) |
| **Verwante techniek** | [T1114.003](T1114.003-email-forwarding-rule.md) — de regel; dit bestand gaat over het lezen zelf |
| **Status van deze detectie** | KQL niet uitgevoerd tegen een productie-tenant — zie [TESTING.md](../teststatus.md) |

## Aanbeveling

> ### `SENTINEL-RULE` — bouw hier een eigen analytic rule
>
> Er is géén alert policy die vuurt wanneer iemand mail leest. `MailItemsAccessed`
> is een audit-event, geen detectie: het levert nooit uit zichzelf een alert op.
> Ook het toekennen van mailboxdelegatie (`Add-MailboxPermission`,
> `Add-RecipientPermission`) heeft geen standaard alert — de enige policy in de
> categorie *Permissions* is `Elevation of Exchange admin privilege` (severity
> **Low**), en die gaat over rolgroepen, niet over mailboxrechten. Wie wil zien
> dat een aanvaller meeleest, moet dat zelf bouwen.

## Is er een Defender-alert voor?

**Nee.** Voor de handeling zelf (mail lezen) bestaat geen alert policy. Twee
dingen die er in de buurt komen, en waarom ze het gat niet dichten:

| | |
|---|---|
| **Alert policy** | `Elevation of Exchange admin privilege` |
| **Standaard severity** | **Low** |
| **Licentie** | E1/F1/G1, E3/F3/G3 of E5/G5 |
| **Waarom niet genoeg** | Microsoft: *"Generates an alert when someone is assigned administrative permissions in your Exchange Online organization."* Dat is de rolgroep Organization Management — niet `Add-MailboxPermission` op één mailbox, wat precies de stille variant is. |
| **Bron** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

| | |
|---|---|
| **Mechanisme** | Defender XDR automatic attack disruption |
| **Wat het is** | Incident-niveau, geen alert policy. Microsoft noemt als voorbeeld van een incidenttitel: *"BEC financial fraud attack launched from a compromised account (attack disruption)"*. |
| **Waarom niet genoeg** | Het vraagt een E5-klasse abonnement (of losse Defender-plannen) én een uitgerolde Defender-suite, en het vuurt pas als de correlatie een lopende aanval herkent — niet bij het eerste dat iemand een mailbox uitleest. Zie [T1657](T1657-financial-theft.md). |
| **Bron** | https://learn.microsoft.com/en-us/defender-xdr/automatic-attack-disruption |

Wel relevant: Microsoft noemt `MailItemsAccessed` expliciet als een van de
mailbox-audit-events die aan moeten staan wil attack disruption in Defender for
Office 365 werken (*"At minimum, audit these mailbox events: MailItemsAccessed,
UpdateInboxRules, MoveToDeletedItems, SoftDelete, and HardDelete"*).
Bron: https://learn.microsoft.com/en-us/defender-xdr/configure-attack-disruption

## Licentieniveau

**`MailItemsAccessed` zit in Audit (Standard) en staat standaard aan bij E3.**
De oudere "alleen E5"-framing klopt niet meer.

| | |
|---|---|
| **Microsoft Learn (geverifieerd 22 aug 2026)** | *"The MailItemsAccessed action is part of Audit (Standard) functionality. It's part of Exchange mailbox auditing and is enabled by default for users that are assigned an Office 365 E3/E5 or Microsoft 365 E3/E5 license."* |
| **Bron** | https://learn.microsoft.com/en-us/purview/audit-log-investigate-accounts (ms.date 2026-06-19) |
| **Bevestiging** | In de tabel met mailbox-acties staat `MailItemsAccessed` met een ✔\* (= standaard gelogd) voor Admin, Delegate én Owner, zonder licentievoetnoot. De enige actie mét zo'n voetnoot is `MessageBind` ("available only for users *without* E5/A5/G5 licenses"). Bron: https://learn.microsoft.com/en-us/purview/audit-mailboxes |

**Twee plekken waar de documentatie zichzelf tegenspreekt — noem dit als je met
een licentiediscussie te maken krijgt:**

1. Microsofts eigen pagina *Investigate shared mailbox activities using audit
   logs* zegt bij hetzelfde event nog: *"This command requires Microsoft 365 E5
   licensing to capture `MailItemsAccessed` operations."* Dat is achterhaald.
   Bron: https://learn.microsoft.com/en-us/purview/audit-log-identify-mailboxes
2. CISA AA23-193A (juli 2023) adviseert *"Enable Purview Audit (Premium)
   logging. This logging requires licensing at the G5/E5 level."* Dat klopte
   toen het advies uitkwam, maar geldt niet meer voor dit specifieke event. Het
   inhoudelijke punt van dat advies staat wél nog overeind (zie *Waarom dit BEC
   is*).

Let op: `SearchQueryInitiated` — het event dat vastlegt waar de aanvaller in de
mailbox naar zócht — staat **niet** standaard aan en moet per mailbox worden
ingeschakeld (`Set-Mailbox <identity> -AuditOwner @{Add="SearchQueryInitiated"}`).
Bron: CISA, *Microsoft Expanded Cloud Logs Implementation Playbook* (mei 2026).

## Vier eigenschappen van MailItemsAccessed die je moet kennen

Zonder deze vier lees je de resultaten verkeerd.

**1. Bind versus Sync.** Het toegangstype staat in het veld `MailAccessType`
binnen `OperationProperties`.

| Waarde | Wat het betekent | Wat je ermee moet |
|---|---|---|
| `Bind` | Eén specifiek bericht is geopend. De `InternetMessageId` van elk bericht staat in het record. | Je weet precies wélke mail gelezen is. |
| `Sync` | Een client heeft een hele map gesynchroniseerd. Er staat géén informatie over losse berichten in. | **Beschouw de hele map als gecompromitteerd.** Microsoft: *"All mail items in the synced folder are assumed to be compromised."* |

Sync-operaties worden alleen vastgelegd bij de desktopversie van Outlook voor
Windows of Mac. Heeft de aanvaller gesynchroniseerd, dan kan hij daarna offline
lezen zonder dat er nog iets wordt gelogd.

**2. Bind-operaties worden geaggregeerd.** Alle bind-operaties binnen een
venster van **2 minuten** komen samen in één auditrecord, in het veld `Folders`
binnen `AuditData`. Het aantal geaggregeerde operaties staat in `OperationCount`.
Eén record is dus niet één gelezen mail.

**3. Duplicaten worden weggefilterd.** Microsoft filtert dubbele bind-operaties
voor dezelfde `InternetMessageId` binnen **een uur**, en sync-operaties op
uurintervallen. Uitzondering: verschilt één van `ClientIPAddress`,
`ClientInfoString`, `ParentFolder`, `Logon_type`, `MailAccessType`,
`MailboxUPN`, `User` of `SessionId`, dan komt er wél een nieuw record. Dat is
precies waarom een aanvaller met een ander IP of een andere client zichtbaar
blijft naast de gewone gebruiker.

**4. Throttling — en wat er wel en niet in de documentatie staat.**

| | |
|---|---|
| **De bewering** | Meer dan 1.000 `MailItemsAccessed`-records op één mailbox binnen 24 uur → Exchange Online stopt 24 uur met loggen; herkenbaar aan het veld `IsThrottled`. |
| **Wel teruggevonden** | CISA, *Microsoft Expanded Cloud Logs Implementation Playbook* (bijgewerkt mei 2026), samen met Microsoft gepubliceerd: *"MailItemsAccessed events can be throttled if more than 1,000 records are generated on a mailbox in less than 24 hours. When this occurs, MailItemsAccessed activity will not be logged for 24 hours after the mailbox was throttled."* Daar staat ook: throttling geldt niet als een admin ándere mailboxen doorzoekt, minder dan één procent van alle mailboxen in Exchange Online wordt getthrottled, en *"the presence of throttling could be an indication of mailbox misuse or compromise"*. Het veld `IsThrottled` wordt in dezelfde lijst genoemd. |
| **Ook teruggevonden** | Microsofts eigen hunting-repo op GitHub, query *MailItemsAccessed Throttling [Nobelium]*, met dezelfde 1.000-in-24-uur-formulering en een KQL die op `RawEventData['OperationProperties'][1]` test. |
| **Niet teruggevonden** | Op de actuele Microsoft Learn-pagina's is er **niets** over throttling of `IsThrottled` te vinden: niet op *Use MailItemsAccessed to investigate compromised accounts* (ms.date 2026-06-19) en niet op *Learn about properties in Exchange audit records* (ms.date 2026-06-19), die wél `Folders`, `FolderItems`, `OperationCount` en `SessionId` opsomt. Ook een gerichte zoekopdracht binnen learn.microsoft.com op `IsThrottled` levert geen pagina op die het veld beschrijft. |
| **Conclusie** | Het gedrag is door twee gezaghebbende, met Microsoft mede-uitgegeven bronnen bevestigd, waarvan één van mei 2026. Het is **niet** bevestigd op de actuele productdocumentatie. Behandel de exacte drempel van 1.000 als niet-gegarandeerd en bouw de detectie op de aanwezigheid van `IsThrottled`, niet op het zelf tellen tot 1.000. |

Het praktische gevolg is hard: bij een aanvaller die veel leest, valt precies op
het moment dat het ertoe doet je bewijs weg. Een record met `IsThrottled` is
daarom geen ruis maar een van de sterkste signalen in dit hele bestand.

## KQL — Sentinel (OfficeActivity)

```kql
// Mailtoegang met het toegangstype en de throttling-vlag eruit gehaald.
// MailAccessType en IsThrottled zitten als Name/Value-paren in
// OperationProperties; extract() is bewust gebruikt in plaats van een
// positie-index, want de volgorde van die array is niet gedocumenteerd.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation =~ "MailItemsAccessed"
| extend OpProps = tostring(OperationProperties)
| extend MailAccessType = extract(@'"Name"\s*:\s*"MailAccessType"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, OpProps)
| extend IsThrottled    = extract(@'"Name"\s*:\s*"IsThrottled"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, OpProps)
| project TimeGenerated, UserId, MailboxOwnerUPN, Logon_Type, MailAccessType, IsThrottled,
          ClientIP, ClientInfoString, ClientAppId, AppId, Folders, OperationProperties
| order by TimeGenerated desc
```

Drie filters die je hierop zet, in volgorde van opbrengst:

```kql
// (a) Throttling: het logboek is gestopt. Altijd onderzoeken.
| where IsThrottled =~ "True"

// (b) Sync: de hele map is weg. Er staat niet in wélke berichten.
| where MailAccessType =~ "Sync"

// (c) Toegang door een ander dan de eigenaar (Delegate = 2, Admin = 1).
| where Logon_Type !in ("0", "Owner")
```

## KQL — Defender XDR advanced hunting (CloudAppEvents)

```kql
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where ActionType == "MailItemsAccessed"
| extend OpProps         = tostring(RawEventData.OperationProperties)
| extend MailAccessType  = extract(@'"Name":"MailAccessType","Value":"([^"]+)"', 1, OpProps)
| extend IsThrottled     = extract(@'"Name":"IsThrottled","Value":"([^"]+)"', 1, OpProps)
| extend AccessingAppId  = tostring(RawEventData.AppId)
| extend ClientInfo      = tostring(RawEventData.ClientInfoString)
| extend MailboxSession  = tostring(RawEventData.SessionId)
| extend MailboxUPN      = tostring(RawEventData.MailboxOwnerUPN)
| project Timestamp, AccountDisplayName, AccountObjectId, MailboxUPN, IPAddress,
          MailAccessType, IsThrottled, AccessingAppId, ClientInfo, MailboxSession
| order by Timestamp desc
```

## Hunting-heuristieken uit de CISA-playbook

De CISA-playbook (mei 2026) geeft twee bruikbare methodes. Beide zijn in dit
bestand overgenomen omdat ze niet op een alert leunen.

**Eerste keer dat een AppId een mailbox benadert.** Trend het aantal
mailtoegangen per applicatie over de tijd; een piek of een onbekende applicatie
is het signaal. CISA's variant, licht aangepast zodat de nieuwe AppIds er zelf
uit komen in plaats van dat je een grafiek moet aflezen:

```kql
// Defender XDR — AppIds die in de laatste 24 uur voor het eerst een mailbox
// benaderen, gemeten tegen de voorgaande 29 dagen.
let baseline = CloudAppEvents
    | where Timestamp between (ago(30d) .. ago(1d))
    | where ActionType == "MailItemsAccessed"
    | distinct AppId = tostring(RawEventData.AppId);
CloudAppEvents
| where Timestamp > ago(1d)
| where ActionType == "MailItemsAccessed"
| extend AppId = tostring(RawEventData.AppId)
| where AppId !in (baseline)
| summarize Mailboxes = dcount(AccountObjectId), Events = count(),
            Voorbeeld = any(tostring(RawEventData.ClientInfoString)) by AppId
| order by Mailboxes desc
```

De onbewerkte CISA-versie, voor wie liever naar een timechart kijkt:

```kql
CloudAppEvents
| where ActionType == "MailItemsAccessed"
| extend Accessing_AppId = tostring(RawEventData.AppId)
| summarize count() by bin(Timestamp,1d), Accessing_AppId
| render timechart
```

```kql
OfficeActivity
| where Operation == "MailItemsAccessed"
| summarize count() by bin(TimeGenerated,1d), AppId
| render timechart
```

**Pivoteren op SessionId.** `SessionId` is een GUID in het Entra-token en
verandert alleen als de gebruiker opnieuw authenticeert. Daarmee groepeer je
alles wat in één logon-sessie is gebeurd, los van IP-adres en user agent — die
wisselt een aanvaller moeiteloos. Reactief, als je één verdacht IP hebt:

```kql
// Defender XDR — welke mail is gelezen in de sessies vanaf een verdacht IP.
// EntraIdSignInEvents vereist Entra ID P2. Tot 19 okt 2026 heet deze tabel
// ook nog AADSignInEventsBeta; die wordt dan automatisch gemigreerd.
let bad_sessions = materialize (
    EntraIdSignInEvents
    | where IPAddress == "x.x.x.x"          // <-- aanpassen
    | where isnotempty(SessionId)
    | distinct SessionId
);
CloudAppEvents
| where ActionType == "MailItemsAccessed"
| where tostring(RawEventData.SessionId) in (bad_sessions)
| project Timestamp, AccountDisplayName, IPAddress,
          MailAccessType = tostring(RawEventData.OperationProperties),
          Folders = RawEventData.Folders
```

## Mailboxdelegatie: de stille variant van meelezen

Een aanvaller die niet wil dat elke sessie op het slachtofferaccount zichtbaar
is, geeft zichzelf rechten op de mailbox en leest verder vanaf zijn eigen
account. Dat overleeft een wachtwoordwijziging, net als een forwardingregel.
Vier handelingen, en wat de audit erover zegt:

| Handeling | Wat het geeft | Gedocumenteerd als audit-activiteit? |
|---|---|---|
| `Add-MailboxPermission` | FullAccess op andermans mailbox | **Ja.** Microsoft: *"An administrator assigned the FullAccess mailbox permission to a user (known as a delegate) to another person's mailbox."* |
| `Remove-MailboxPermission` | Intrekken van diezelfde rechten — een aanvaller ruimt op | **Ja**, met eigen omschrijving. |
| `Add-RecipientPermission` | Send-As: berichten versturen die van de mailboxeigenaar lijken te komen | **Niet als aparte regel** op de activiteitenpagina teruggevonden. De cmdlet zelf is gedocumenteerd (*"Use the Add-RecipientPermission cmdlet to add SendAs permission"*, enige geldige `-AccessRights` is `SendAs`) en Exchange-admin-cmdlets komen als `RecordType` **ExchangeAdmin** in het auditlog met de gebruikte parameters in `Parameters`. Filter er dus op, maar weet dat de dekking niet expliciet gedocumenteerd is. |
| `Set-Mailbox -GrantSendOnBehalfTo` | Send-on-behalf | Idem: `Set-Mailbox` is een gedocumenteerde audit-operatie voor mailboxinstellingen; de specifieke parameter zit in `Parameters`. |
| `UpdateFolderPermissions` | Rechten op één map, bijvoorbeeld alleen de Inbox | **Ja**, en standaard gelogd (✔\*) voor Admin, Delegate én Owner. Microsoft merkt op dat `AddFolderPermissions`, `ModifyFolderPermissions` en `RemoveFolderPermissions` hierin zijn opgenomen en niet apart worden gelogd — gebruik die waarden niet. |

```kql
// Sentinel — toekenning van mailboxrechten, Send-As, Send-on-behalf en
// mappermissies in één rule. Set-Mailbox is bewust op parameter gefilterd,
// anders vuurt hij op elke mailboxwijziging.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation in~ ("Add-MailboxPermission", "Remove-MailboxPermission",
                       "Add-RecipientPermission", "Remove-RecipientPermission",
                       "Set-Mailbox", "UpdateFolderPermissions")
| extend Params = tostring(Parameters)
| where Operation !~ "Set-Mailbox" or Params has "GrantSendOnBehalfTo"
| extend Trustee     = extract(@'"Name"\s*:\s*"(?:Trustee|User)"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, Params)
| extend AccessRight = extract(@'"Name"\s*:\s*"AccessRights"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, Params)
| project TimeGenerated, UserId, Operation, MailboxOwnerUPN, Trustee, AccessRight,
          ClientIP, ExternalAccess, ResultStatus, Params
| order by TimeGenerated desc
```

```kql
// Defender XDR — dezelfde handelingen.
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where ActionType in~ ("Add-MailboxPermission", "Remove-MailboxPermission",
                        "Add-RecipientPermission", "Remove-RecipientPermission",
                        "Set-Mailbox", "UpdateFolderPermissions")
| extend Params = tostring(RawEventData.Parameters)
| where ActionType !~ "Set-Mailbox" or Params has "GrantSendOnBehalfTo"
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, IPAddress,
          Mailbox = tostring(RawEventData.MailboxOwnerUPN), Params
| order by Timestamp desc
```

Nuttige aanscherping bij een lopend onderzoek: `FolderBind` legt vast dat een
delegate een map opent, maar staat **niet** standaard aan en logt de eigenaar
niet. Aanzetten kan per mailbox met
`Set-Mailbox <mailbox> -AuditDelegate @{Add="FolderBind"}`. Microsoft
consolideert die records: één record per map per 24 uur.

## Waarom dit BEC is

Voor BEC is dit het event dat bepaalt of je na afloop iets kunt zeggen. Een
aanvaller die de facturenstroom wil nabootsen, moet eerst lezen wie met wie over
geld praat. CISA en de FBI schreven in AA23-193A (12 juli 2023) over een
federale organisatie die een inbraak in Exchange Online uitsluitend opmerkte aan
`MailItemsAccessed`-records met een onverwachte `ClientAppID` en `AppID`, en
concludeerden letterlijk: *"CISA and FBI are not aware of other audit logs or
events that would have detected this activity."*

Daarmee is dit het enige event waarmee je achteraf kunt vaststellen wélke mail
een aanvaller heeft gelezen — en dus of je een meldplicht hebt. Bij `Sync` kun
je dat niet per bericht: dan is het de hele map. En bij throttling kun je het
voor 24 uur helemaal niet.

De schaal waarom het gaat: de FBI ontving in 2025 24.768 BEC-meldingen met een
gerapporteerde schade van $3.046.598.558 (IC3 Annual Report 2025), tegen 21.442
meldingen en $2.770.151.146 in 2024.
