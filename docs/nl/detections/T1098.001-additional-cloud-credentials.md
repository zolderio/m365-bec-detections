# T1098.001 — Account Manipulation: Additional Cloud Credentials

| | |
|---|---|
| **Naam in het advies** | Additional Cloud Credentials — het toevoegen van extra geheimen of certificaten aan cloud-accounts of apps |
| **Naam in MITRE ATT&CK** | Account Manipulation: Additional Cloud Credentials |
| **MITRE-tactiek** | Persistence (TA0003) en Privilege Escalation (TA0004) |
| **Whitepaper-maatregel** | 009 — OAuth-app consent beperken of uitschakelen (prioriteit Hoog) |
| **Verwante technieken** | [T1671](T1671-illicit-consent-grant.md) — consent aan een nieuwe app; [T1556.006](T1556.006-mfa-modification.md) — dezelfde maatregel, de MFA-kant |
| **Status van deze detectie** | KQL niet uitgevoerd tegen een productie-tenant — zie [teststatus](../teststatus.md) |

## Aanbeveling

> ### `SENTINEL-RULE` — bouw hier een eigen analytic rule
>
> Op de handeling zelf — een secret of certificaat toevoegen aan een bestaande
> service principal — bestaat **geen** alert. Niet in Purview, niet in Entra ID
> Protection. Wat er wel is, zijn app governance-alerts, en die hebben twee
> eigenschappen die ze ongeschikt maken als primaire detectie: ze vereisen een
> Defender for Cloud Apps-licentie (dus niet E1/E3), en ze vuren pas als de app
> ná het toevoegen van de credential ook nog anomaal gedrag vertoont — soms
> dagen later, soms nooit. De credentialtoevoeging zelf staat wel netjes in de
> Entra-auditlog. Bouw daar de regel op. Heb je app governance, zet het aan als
> tweede laag, niet als eerste.

## Is er een Defender-alert voor?

**Niet op de handeling. Wel op het gedrag dat er soms op volgt.**

Deze app governance-alerts raken T1098.001 direct. Ze komen uit Microsoft
Defender for Cloud Apps en zijn per stuk **Medium** of **Low**:

| Alert | Severity | MITRE-ID volgens Microsoft |
|---|---|---|
| `App made anomalous Graph calls to Exchange workload post certificate update or addition of new credentials` | **Medium** | T1098.001, T1114 |
| `App accessed from unusual location post certificate update` | **Low** | T1098 |
| `App accessed from unusual location made anomalous Graph calls post certificate update` | **Medium** | T1098 |
| `Anomalous OneDrive activity by app that just updated or added new credentials` | **Medium** | — |
| `Anomalous SharePoint activity by app that just updated or added new credentials` | **Medium** | — |

Let op de formulering in alle vijf: *post* certificate update. Het alert is een
gevolgdetectie. Er is geen alert dat vuurt op het moment dat de credential wordt
toegevoegd.

## Benodigde databron

| Platform | Tabel | Wat er onboard moet zijn |
|---|---|---|
| Microsoft Sentinel | `AuditLogs` | Data connector **Microsoft Entra ID**. Die wordt automatisch ingeschakeld zodra je in Entra ID een diagnostic setting aanmaakt die de auditlogs naar een Log Analytics workspace stuurt. |
| Microsoft Sentinel | `AADServicePrincipalSignInLogs` | Zelfde connector, maar de logcategorie **ServicePrincipalSignInLogs** moet apart in de diagnostic setting zijn aangevinkt. Wordt vaak vergeten. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps met de Microsoft 365-connector (**Settings > Cloud apps > App connectors**, vinkje *Microsoft 365 activities*). Retentie 30 dagen. |

De prerequisites voor het routeren van Entra-logs naar Log Analytics noemen
géén Entra ID-licentie-eis; wel een Azure-subscription, een Log Analytics
workspace en minimaal de rol Security Administrator. De ingestie kost geld —
Microsoft rekent met circa 2 KB per auditlog-event.

Deze detectie hangt **niet** aan maatregel 012 (Unified Audit Log): de
Entra-auditlog loopt via diagnostic settings, niet via de UAL. De
`CloudAppEvents`-variant leunt wel op de Microsoft 365-connector van Defender
for Cloud Apps.

## KQL — Sentinel (AuditLogs): credentials toegevoegd aan een app of service principal

```kql
// De twee activiteiten waar het om gaat. De namen zijn een valkuil: de
// Entra-auditreferentie schrijft "Update application - Certificates and secrets
// management" met een gewoon koppelteken, terwijl Microsofts eigen hunting-query
// voor dezelfde activiteit een en-dash (–) en een spatie op het eind gebruikt.
// Daarom filteren we met startswith en niet met een exacte string.
let lookback = 30d;
AuditLogs
| where TimeGenerated > ago(lookback)
| where Category == "ApplicationManagement"
| where OperationName startswith "Add service principal credentials"
     or OperationName startswith "Update application"
        and OperationName has "Certificates and secrets"
| where Result == "success"
| extend Actor = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName))
| extend ActorIP = tostring(InitiatedBy.user.ipAddress)
| extend TargetApp = tostring(TargetResources[0].displayName)
| extend TargetAppId = tostring(TargetResources[0].id)
// De toegevoegde sleutel staat als KeyDescription in modifiedProperties; de
// waarde verraadt of het een secret of een certificaat is en hoe lang hij geldig is.
| extend KeyChange = TargetResources[0].modifiedProperties
| project TimeGenerated, OperationName, Actor, ActorIP, TargetApp, TargetAppId,
          KeyChange, CorrelationId
| order by TimeGenerated desc
```

## KQL — Sentinel: het Nobelium-patroon (consent, daarna credentials, door iemand anders)

```kql
// Admin geeft consent aan een app; kort daarna zet een ándere identiteit er een
// secret op. Dat is de volgorde die Microsoft bij Nobelium/Midnight Blizzard
// beschrijft. Losse events zijn beide verdedigbaar; de combinatie niet.
let window = 7d;
let consent =
    AuditLogs
    | where TimeGenerated > ago(30d)
    | where OperationName == "Consent to application"
    | where Result == "success"
    | extend ConsentBy = tostring(InitiatedBy.user.userPrincipalName)
    | extend AppObjectId = tostring(TargetResources[0].id)
    | project ConsentTime = TimeGenerated, ConsentBy, AppObjectId,
              AppName = tostring(TargetResources[0].displayName);
let secrets =
    AuditLogs
    | where TimeGenerated > ago(30d)
    | where OperationName startswith "Add service principal credentials"
         or (OperationName startswith "Update application" and OperationName has "Certificates and secrets")
    | where Result == "success"
    | extend SecretBy = tostring(InitiatedBy.user.userPrincipalName)
    | extend AppObjectId = tostring(TargetResources[0].id)
    | project SecretTime = TimeGenerated, SecretBy, AppObjectId;
consent
| join kind=inner secrets on AppObjectId
| where SecretTime between (ConsentTime .. ConsentTime + window)
// Andere actor dan degene die consent gaf: dat is het signaal.
| where tolower(ConsentBy) != tolower(SecretBy)
| project ConsentTime, ConsentBy, SecretTime, SecretBy, AppName, AppObjectId
| order by SecretTime desc
```

## KQL — Defender XDR advanced hunting (CloudAppEvents)

```kql
// Bewerking van de door Microsoft gepubliceerde hunting-query
// "CredentialsAddAfterAdminConsentedToApp[Nobelium]". Entra-auditevents komen in
// CloudAppEvents binnen onder Application "Office 365"; let op de punt aan het
// eind van de ActionType-waarden, die staat er in Microsofts eigen query ook.
let lookback = 30d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Office 365"
| where ActionType startswith "Add service principal credentials"
     or ActionType startswith "Update application"
| where ActionType has_any ("service principal credentials", "Certificates and secrets")
| extend spnID = tostring(RawEventData.Target[3].ID)
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, spnID,
          IPAddress, UserAgent, IsAdminOperation, RawEventData
| order by Timestamp desc
```

Microsofts originele query filtert met
`ActionType == "Add service principal credentials."` en
`ActionType == "Update application – Certificates and secrets management "`.
Die tweede waarde bevat een en-dash en een afsluitende spatie. Wij gebruiken
`startswith` om niet op die typografie te struikelen. Draai
`CloudAppEvents | where Application == "Office 365" | distinct ActionType` om
vast te stellen welke schrijfwijze jouw tenant produceert.

## KQL — de credential zien wórden gebruikt (AADServicePrincipalSignInLogs)

```kql
// Een nieuwe credential is pas een incident als hij ook wordt gebruikt.
// ServicePrincipalCredentialKeyId identificeert de sleutel waarmee de service
// principal inlogde; een key-id dat niet eerder is gezien, is het bewijs.
let baseline = 30d;
let recent = 1d;
let known =
    AADServicePrincipalSignInLogs
    | where TimeGenerated between (ago(baseline) .. ago(recent))
    | distinct ServicePrincipalId, ServicePrincipalCredentialKeyId;
AADServicePrincipalSignInLogs
| where TimeGenerated > ago(recent)
| where ResultType == "0"
| join kind=leftanti known on ServicePrincipalId, ServicePrincipalCredentialKeyId
| project TimeGenerated, ServicePrincipalName, ServicePrincipalId, AppId,
          ServicePrincipalCredentialKeyId, ClientCredentialType, IPAddress,
          ResourceDisplayName, LocationDetails
| order by TimeGenerated desc
```

## Waarom dit BEC is

Een secret op een service principal is de vorm van persistentie die een
wachtwoordreset, een MFA-reset en een sessie-intrekking allemaal overleeft, en
die geen gebruikersinteractie meer nodig heeft. Microsoft beschrijft precies
deze stap in de responderguidance bij de aanval op de eigen corporate tenant
(25 januari 2024): de actor *"created additional malicious OAuth
applications"*, compromitteerde daarnaast een bestaande legacy test-OAuth-app
met verhoogde rechten, en gebruikte die *"to grant them the Office 365 Exchange
Online full_access_as_app role, which allows access to mailboxes"*.

MITRE noemt bij T1098.001 als procedurevoorbeeld APT29, dat tijdens de
SolarWinds-compromittering credentials toevoegde aan OAuth-applicaties en
service principals, en Storm-0501, dat administrator-wachtwoorden zonder MFA
resette en vervolgens een eigen MFA-methode registreerde — de combinatie die in
[T1556.006](T1556.006-mfa-modification.md) staat.

Bij mkb-BEC is de variant vaak eenvoudiger: één app-registratie met
`Mail.Read`, een secret met een looptijd van twee jaar, en een stille lezer in
de directiemailbox.
