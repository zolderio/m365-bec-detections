# T1562.001 — Impair Defenses: Disable or Modify Tools

| | |
|---|---|
| **MITRE tactic** | Defense Evasion (advisory) — see *Numbering* below |
| **Advisory phase** | 08. Defense Evasion |
| **Advisory measures** | 011 — Forward security alerts (High) · 012 — Enable the Unified Audit Log (High) · 013 — Monitoring for configuration drift (High) |
| **Related technique** | [T1564.008](T1564.008-email-hiding-rules.md) — same measures, different action |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — there is no alert here, build it yourself
>
> Microsoft provides **no** default alert policy that fires when auditing is
> switched off. The list of default alert policies has four categories
> (Information governance, Mail flow, Permissions, Threat management) and none
> of them contains one. So there is also no severity to raise. Build two things:
> an event rule on the cmdlets that switch off the logging, and a watchdog on
> the absence of log records. The second is emphatically not an event detection
> — see the warning with that query.

## Numbering: what the advisory says and what ATT&CK now does

The NCSC/Cyclotron advisory ties measures 011–013 to **T1562.001**
(*Impair Defenses: Disable or Modify Tools*). We keep that numbering in this
repo, because the advisory is the source.

In ATT&CK v19 that structure has been rebuilt.
`attack.mitre.org/techniques/T1562/001/` and `/T1562/` now redirect to
**T1685 — Disable or Modify Tools**, which is now a standalone technique under
the tactic *Defense Impairment*. The sub-technique describing the disabling of
cloud logging, **T1562.008** (*Disable or Modify Cloud Logs*), has been
withdrawn in favour of **T1685.002 — Disable or Modify Cloud Log**. In substance
that is the technique this file detects. If you map this repo to an ATT&CK
navigator of v19 or newer, T1685.002 is the correct target.

## Is there a Defender alert for this?

**No, not for disabling auditing.** There is one adjacent policy that can catch
the run-up to this action:

| | |
|---|---|
| **Alert policy** | `Elevation of Exchange admin privilege` |
| **Default severity** | **Low** |
| **Licensing** | E1/F1/G1, E3/F3/G3 or E5/G5 — no add-on required |
| **What it is** | Fires when someone is granted administrative rights in Exchange Online, for example on being added to the Organization Management role group. That is precisely the permissions step that must precede `Set-AdminAuditLogConfig`. |
| **Limitation** | Fires on the permissions change, not on the disabling of the logging itself. Severity `Low`, and raising it is not demonstrably possible for a System policy — see the README. |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

**Note the coverage gap in Defender for Cloud Apps.** The anomaly policy
*Suspicious email deletion activity* was switched off as of June 2025, together
with *Suspicious inbox manipulation rules*, *Activity from suspicious IP
addresses* and six other legacy policies. That affects this technique
indirectly: since then, clearing traces in the mailbox is no longer covered by a
default MDCA detection.
Source: https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

## What the attacker does exactly

Four actions, in increasing order of stealth:

| Action | Cmdlet | Effect |
|---|---|---|
| Switch off the Unified Audit Log | `Set-AdminAuditLogConfig -UnifiedAuditLogIngestionEnabled $false` | Microsoft: *"If you turn off auditing in Microsoft 365, you can't use the Office 365 Management Activity API or Microsoft Sentinel to access auditing data […] Running the **Search-UnifiedAuditLog** cmdlet in Exchange Online PowerShell also returns no results."* The entire SIEM feed disappears. |
| Switch off mailbox auditing organisation-wide | `Set-OrganizationConfig -AuditDisabled $true` | Microsoft: *"From the time you turn off mailbox auditing on by default, no mailbox actions are audited, even if mailbox auditing is enabled on a mailbox."* |
| Make one user invisible | `Set-MailboxAuditBypassAssociation -Identity <x> -AuditBypassEnabled $true` | Microsoft: prevents *"all mailbox actions by the specified users from being logged, regardless of where the actions occur"* — including delegate actions on other mailboxes. Surgical, and therefore the hardest to spot. |
| Strip audit actions per mailbox | `Set-Mailbox -AuditOwner`/`-AuditDelegate`/`-AuditAdmin` | Removes individual actions from the audit set, for example `UpdateInboxRules` or `MailItemsAccessed`. The mailbox still appears to be audited normally; only what you wanted to see is missing. Recognisable by a changed `DefaultAuditSet` value. |

Sources: https://learn.microsoft.com/en-us/purview/audit-log-enable-disable and
https://learn.microsoft.com/en-us/purview/audit-mailboxes

The good news: the first action logs itself. Microsoft: *"Your organization
audits changes to the auditing status. Audit records are logged when auditing is
turned on or turned off."* — findable with
`Search-UnifiedAuditLog -Operations Set-AdminAuditLogConfig`. There is one
record before it goes quiet. That single record is the detection.

## Required data source

| Platform | Table | What must be onboarded |
|---|---|---|
| Microsoft Sentinel | `OfficeActivity` | Data connector **Microsoft 365** (Exchange workload enabled). Exchange admin cmdlets arrive as `RecordType` **ExchangeAdmin** (Office 365 Management Activity API, record type 1). |
| Microsoft Sentinel | `AuditLogs` | Diagnostic setting on Microsoft Entra ID with category **AuditLogs** to the Log Analytics workspace. Needed for the drift variant under measure 013. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps integration with **Microsoft 365 activities** enabled. Whether Exchange admin cmdlets land here in full is **not exhaustively documented**; Microsoft's own playbook does use `ActionType == "Set-Mailbox"` in this table. |

This detection depends entirely on measure 012. If the UAL is off, there is
nothing — not even to establish that it is off.

## KQL — Sentinel (OfficeActivity): the disabling itself

<!-- query
platform: sentinel
name: Audit logging disabled or audit actions stripped in Exchange Online
technique: T1562.001
severity: High
tactics: [DefenseEvasion]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// Four ways to silence the logging, in one go.
// This is the only hard event detection for this technique. Put it on a short
// query frequency: after the first record the source may fall silent.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation in~ (
      "Set-AdminAuditLogConfig",            // Unified Audit Log on/off
      "Set-OrganizationConfig",             // mailbox auditing organisation-wide
      "Set-MailboxAuditBypassAssociation",  // audit bypass per user
      "Set-Mailbox")                        // strip audit actions per mailbox
| extend Params = tostring(Parameters)
| extend Finding = case(
      Params has "UnifiedAuditLogIngestionEnabled" and Params has "False", "UAL disabled",
      Params has "AuditDisabled"                   and Params has "True",  "Mailbox auditing disabled org-wide",
      Params has "AuditBypassEnabled"              and Params has "True",  "Audit bypass enabled for a user",
      Params has_any ("AuditOwner", "AuditDelegate", "AuditAdmin", "AuditEnabled"), "Per-mailbox audit actions changed",
      "")
| where isnotempty(Finding)
| extend ClientIPAddress = case(ClientIP has ".", tostring(split(ClientIP, ":")[0]),
                                ClientIP has "[", tostring(trim_start(@'[[]', tostring(split(ClientIP, "]")[0]))),
                                ClientIP)
| project TimeGenerated, Finding, UserId, Operation, ResultStatus,
          ClientIPAddress, ExternalAccess, OriginatingServer, Params
| order by TimeGenerated desc
```

In a healthy organisation each of these four is a planned, announced action.
Alert on all four at `High` and tune with an allowlist on service accounts, not
with a threshold.

## KQL — Defender XDR advanced hunting (CloudAppEvents)

<!-- query
platform: defender-xdr
name: Audit configuration changes in the cloud app audit trail
technique: T1562.001
severity: High
tactics: [DefenseEvasion]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Microsoft Exchange Online"
| where ActionType in~ ("Set-AdminAuditLogConfig", "Set-OrganizationConfig",
                        "Set-MailboxAuditBypassAssociation", "Set-Mailbox")
| extend Params = tostring(RawEventData.Parameters)
| where Params has_any ("UnifiedAuditLogIngestionEnabled", "AuditDisabled",
                        "AuditBypassEnabled", "AuditOwner", "AuditDelegate",
                        "AuditAdmin", "AuditEnabled")
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType,
          IsAdminOperation, IPAddress, CountryCode, UserAgent, Params
| order by Timestamp desc
```

## KQL — Sentinel: the watchdog on absent logs

> **This is not an event detection.** It is a health measurement on the data
> source itself. It also fires on a connector failure, on a workspace migration,
> during a holiday week and on a licence change. Treat a hit as "find out why it
> is quiet", not as "there is an attacker". Include it anyway: it is the only
> coverage for the scenarios in which the attacker switches off the logging
> before you had the event rule above running live, and for the case in which
> the source disappears by some other route.

<!-- query
platform: sentinel
name: Unexpected drop to zero in the audit record volume of a workload
technique: T1562.001
severity: Medium
tactics: [DefenseEvasion]
interval: PT1H
lookback: P14D
parameters: []
deployable: true
-->
```kql
// Is the audit feed per workload falling silent unexpectedly?
// Compares the hourly volume of the last 14 days with itself; a hard drop to
// zero is the signal.
let window = 14d;
OfficeActivity
| where TimeGenerated > ago(window)
| make-series Records = count() default = 0
    on TimeGenerated from ago(window) to now() step 1h
    by OfficeWorkload
| extend (Anomaly, Score, Baseline) = series_decompose_anomalies(Records, 2.5, -1, "linefit")
| mv-expand TimeGenerated to typeof(datetime), Records to typeof(long),
            Anomaly to typeof(int), Score to typeof(double), Baseline to typeof(double)
| where Anomaly == -1            // only drops, no spikes
| where Baseline > 10             // ignore workloads that barely log anyway
| project TimeGenerated, OfficeWorkload, Records, Baseline = round(Baseline, 1), Score = round(Score, 2)
| order by TimeGenerated desc
```

A simpler variant that works perfectly well as a scheduled rule with
`triggerThreshold: 0`, and that is less sensitive to seasonal noise:

<!-- query
platform: sentinel
name: No Exchange audit records for three hours while the baseline is well above zero
technique: T1562.001
severity: Medium
tactics: [DefenseEvasion]
interval: PT1H
lookback: P7D
parameters: []
deployable: true
-->
```kql
// No Exchange audit record at all in the past 3 hours, while the preceding week
// averaged well above zero.
let recent = OfficeActivity
    | where TimeGenerated > ago(3h) and OfficeWorkload =~ "Exchange"
    | count;
let baseline = OfficeActivity
    | where TimeGenerated between (ago(7d) .. ago(3h)) and OfficeWorkload =~ "Exchange"
    | summarize PerThreeHours = count() / 56.0;
recent
| extend Baseline = toscalar(baseline)
| where Count == 0 and Baseline > 10
```

## Why this matters for BEC

In BEC, the attacker's profit is a function of how long they read along
unseen. The advisory says so itself: *"Attackers also frequently attempt to
disable logging or erase traces in order to remain undetected; external log
forwarding and active monitoring of the status of the UAL prevent this blind
spot from arising."*

The cost of the gap is asymmetrical. Without the UAL there is no way to
establish which mailboxes were accessed, which rules were in place and which
invoices were manipulated — precisely the questions that have to be answered
after a BEC incident towards the insurer, the accountant and the regulator. The
whitepaper puts it as: *"Without active audit logging, an organisation is blind
after a breach."*

That is also why measure 011 (forwarding alerts to a distribution group instead
of to a single administrator) sits in this cluster: the alerts from
`Office365Alerts@microsoft.com` are often the only signal left when the rest of
the logging has been silenced, and they must not end up in a single personal
inbox.
