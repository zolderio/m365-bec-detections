# T1114.003 — Email Forwarding Rule

| | |
|---|---|
| **MITRE tactic** | Collection |
| **Advisory measure** | 016 — Blocking automatic email forwarding (priority High) |
| **Related technique** | [T1564.008](T1564.008-email-hiding-rules.md) — the same events, a different purpose |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> The Defender alert exists and does not require E5, but it does not fully
> cover the activity: rules created from the Outlook desktop client fall
> outside it, and those are precisely the ones an administrator can see least
> well. Do switch the alert on as a safety net, but do not rely on it for
> coverage.
>
> Raising the severity is not a way out: this is a **System** policy, and
> according to Microsoft that means you can only turn it on or off and set the
> notification recipients — *"The other settings for these policies can't be
> edited."* See the README for the contradiction in Microsoft's documentation
> on this point.

## Is there a Defender alert for this?

**Partly.** A default alert policy exists, but with two limitations that
determine whether you can build detection on it.

| | |
|---|---|
| **Alert policy** | `Creation of forwarding/redirect rule` |
| **Default severity** | **Informational** |
| **Licensing** | E1/F1/G1, E3/F3/G3 or E5/G5 — no add-on required |
| **Limitation 1** | Microsoft: *"This policy only tracks inbox rules that are created using Outlook on the web (formerly known as Outlook Web App) or Exchange Online PowerShell."* A rule created from the Outlook desktop client produces **no** alert. |
| **Limitation 2** | The policy only covers rules that forward or redirect. A rule that merely moves or deletes mail falls under neither this nor any other policy — see T1564.008. |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

A related policy at a more usable level:

| | |
|---|---|
| **Alert policy** | `Suspicious email forwarding activity` |
| **Default severity** | **High** |
| **Licensing** | E1/F1/G1, E3/F3/G3 or E5/G5 |
| **What it is** | Does not fire on the creation of the rule, but heuristically on mail sent to a suspicious external account. It therefore only detects after data has already left. |

Retired, do not build on it: the Defender for Cloud Apps policy
`Suspicious inbox forwarding` was switched off as a legacy policy in June 2025.
Source: https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

## Required data source

| Platform | Table | What must be onboarded |
|---|---|---|
| Microsoft Sentinel | `OfficeActivity` | Data connector **Microsoft 365** (Exchange workload enabled). Requires an enabled Unified Audit Log — advisory measure 012. |
| Defender XDR advanced hunting | `CloudAppEvents` | No connector; available by default with the Defender for Cloud Apps integration. Retention 30 days. |

Without measure 012 (UAL enabled) both queries return nothing. That is not a
detection problem but a logging problem.

## KQL — Sentinel (OfficeActivity)

```kql
// Inbox rule created or modified with a forward, redirect or
// forward-as-attachment action. Deliberately also covers UpdateInboxRules,
// because that is the operation the Outlook desktop client writes and the one
// the default alert policy does not fire on.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| extend RuleParameters = tostring(Parameters)
| where RuleParameters has_any ("ForwardTo", "ForwardAsAttachmentTo", "RedirectTo")
| extend TargetAddress = extract(@"(?i)(?:ForwardTo|ForwardAsAttachmentTo|RedirectTo)""?,""?Value""?:""?\[?([^""\]]+)", 1, RuleParameters)
| project TimeGenerated, UserId, Operation, ClientIP, TargetAddress, RuleParameters, OriginatingServer
| order by TimeGenerated desc
```

## KQL — Defender XDR advanced hunting (CloudAppEvents)

```kql
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where ActionType in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| extend Params = tostring(RawEventData.Parameters)
| where Params has_any ("ForwardTo", "ForwardAsAttachmentTo", "RedirectTo")
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, IPAddress, Params
| order by Timestamp desc
```

## Narrowing to external recipients

Forwarding to an internal address is usually legitimate. In both queries,
replace the last filter line to keep only external destinations:

```kql
| extend TargetDomain = tolower(tostring(split(TargetAddress, "@")[1]))
| where isnotempty(TargetDomain)
| where TargetDomain !in~ ("yourdomain.example", "yourseconddomain.example")   // <-- adjust
```

## Why this matters for BEC

The attacker reads along without logging in again, and the rule survives a
password change and an MFA reset. From its own incident work, CISA describes
rules that move incoming warnings to the *RSS Subscriptions* folder so the
victim does not see them (AR21-013A, January 2021). In November 2020 the FBI
warned that rules created in the web client do not sync to the desktop client
and therefore remain invisible to the administrator (PIN 20201125-001).
