# T1098.001 — Account Manipulation: Additional Cloud Credentials

| | |
|---|---|
| **Name in the advisory** | Additional Cloud Credentials — adding extra secrets or certificates to cloud accounts or apps |
| **Name in MITRE ATT&CK** | Account Manipulation: Additional Cloud Credentials |
| **MITRE tactic** | Persistence (TA0003) and Privilege Escalation (TA0004) |
| **Advisory measure** | 009 — Restricting or disabling OAuth app consent (priority High) |
| **Related techniques** | [T1671](T1671-illicit-consent-grant.md) — consent to a new app; [T1556.006](T1556.006-mfa-modification.md) — the same measure, the MFA side |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> For the action itself — adding a secret or certificate to an existing service
> principal — **no** alert exists. Not in Purview, not in Entra ID Protection.
> What does exist are app governance alerts, and they have two properties that
> make them unsuitable as a primary detection: they require a Defender for
> Cloud Apps licence (so not E1/E3), and they only fire once the app also
> displays anomalous behaviour *after* the credential was added — sometimes days
> later, sometimes never. The credential addition itself is recorded properly
> in the Entra audit log. Build the rule on that. If you have app governance,
> enable it as a second layer, not as the first.

## Is there a Defender alert for this?

**Not on the action. Only on the behaviour that sometimes follows it.**

These app governance alerts touch T1098.001 directly. They come from Microsoft
Defender for Cloud Apps and are **Medium** or **Low** individually:

| Alert | Severity | MITRE ID according to Microsoft |
|---|---|---|
| `App made anomalous Graph calls to Exchange workload post certificate update or addition of new credentials` | **Medium** | T1098.001, T1114 |
| `App accessed from unusual location post certificate update` | **Low** | T1098 |
| `App accessed from unusual location made anomalous Graph calls post certificate update` | **Medium** | T1098 |
| `Anomalous OneDrive activity by app that just updated or added new credentials` | **Medium** | — |
| `Anomalous SharePoint activity by app that just updated or added new credentials` | **Medium** | — |

Note the wording in all five: *post* certificate update. The alert is a
consequence detection. There is no alert that fires at the moment the
credential is added.

| | |
|---|---|
| **Licensing for app governance** | *"App governance is available to organizations with a valid Defender for Cloud Apps license."* Defender for Cloud Apps must be present as a standalone product or as part of a licence bundle. |
| **Additional condition** | The organisation's billing address must be in a region other than Singapore, Poland, Italy, Qatar, Israel, Spain, Mexico and Taiwan. App governance is then switched on manually under **Settings > Cloud Apps > App governance**, and is available up to 10 hours later. |
| **Recommended addition** | Microsoft: connect the Microsoft 365 connector, otherwise there is no visibility into the activities and resources the OAuth app accesses. |
| **Alert policies (Purview)** | None. There is no default alert policy for service principal credentials. |
| **Entra ID Protection** | No risk detection for this action in the documented list. |

## Required data source

| Platform | Table | What needs to be onboarded |
|---|---|---|
| Microsoft Sentinel | `AuditLogs` | Data connector **Microsoft Entra ID**. It is enabled automatically as soon as you create a diagnostic setting in Entra ID that sends the audit logs to a Log Analytics workspace. |
| Microsoft Sentinel | `AADServicePrincipalSignInLogs` | Same connector, but the log category **ServicePrincipalSignInLogs** must be ticked separately in the diagnostic setting. It is often forgotten. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps with the Microsoft 365 connector (**Settings > Cloud apps > App connectors**, tick *Microsoft 365 activities*). Retention 30 days. |

The prerequisites for routing Entra logs to Log Analytics do **not** mention an
Entra ID licensing requirement; they do require an Azure subscription, a Log
Analytics workspace and at least the Security Administrator role. Ingestion
costs money — Microsoft reckons with roughly 2 KB per audit log event.

This detection does **not** depend on measure 012 (Unified Audit Log): the
Entra audit log runs through diagnostic settings, not through the UAL. The
`CloudAppEvents` variant does lean on the Microsoft 365 connector of Defender
for Cloud Apps.

## KQL — Sentinel (AuditLogs): credentials added to an app or service principal

<!-- query
platform: sentinel
name: Credential added to an application or service principal
technique: T1098.001
severity: Medium
tactics: [Persistence, PrivilegeEscalation]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// The two activities that matter here. The names are a trap: the
// Entra audit reference writes "Update application - Certificates and secrets
// management" with an ordinary hyphen, while Microsoft's own hunting query
// for the same activity uses an en dash (–) and a trailing space.
// That is why we filter with startswith and not with an exact string.
let lookback = 1d;
AuditLogs
| where TimeGenerated > ago(lookback)
| where Category == "ApplicationManagement"
| where OperationName startswith "Add service principal credentials"
     or OperationName startswith "Update application"
        and OperationName has "Certificates and secrets"
| where Result == "success"
| extend Actor = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName))
| extend ActorIP = tostring(InitiatedBy.user.ipAddress)
| extend TargetApp = tostring(TargetResources[0].displayName)
| extend TargetAppId = tostring(TargetResources[0].id)
// The added key appears as KeyDescription in modifiedProperties; the
// value reveals whether it is a secret or a certificate and how long it is valid.
| extend KeyChange = TargetResources[0].modifiedProperties
| project TimeGenerated, OperationName, Actor, ActorIP, TargetApp, TargetAppId,
          KeyChange, CorrelationId
| order by TimeGenerated desc
```

## KQL — Sentinel: the Nobelium pattern (consent, then credentials, by somebody else)

<!-- query
platform: sentinel
name: Application credential added by a different identity shortly after admin consent
technique: T1098.001
severity: High
tactics: [Persistence, PrivilegeEscalation]
interval: P1D
lookback: P30D
parameters: []
deployable: true
-->
```kql
// An admin grants consent to an app; shortly afterwards a different identity puts
// a secret on it. That is the sequence Microsoft describes for Nobelium/Midnight Blizzard.
// Each event on its own is defensible; the combination is not.
let window = 7d;
let consent =
    AuditLogs
    | where TimeGenerated > ago(30d)
    | where OperationName == "Consent to application"
    | where Result == "success"
    | extend ConsentBy = tostring(InitiatedBy.user.userPrincipalName)
    | extend AppObjectId = tostring(TargetResources[0].id)
    | project ConsentTime = TimeGenerated, ConsentBy, AppObjectId,
              AppName = tostring(TargetResources[0].displayName);
let secrets =
    AuditLogs
    | where TimeGenerated > ago(30d)
    | where OperationName startswith "Add service principal credentials"
         or (OperationName startswith "Update application" and OperationName has "Certificates and secrets")
    | where Result == "success"
    | extend SecretBy = tostring(InitiatedBy.user.userPrincipalName)
    | extend AppObjectId = tostring(TargetResources[0].id)
    | project SecretTime = TimeGenerated, SecretBy, AppObjectId;
consent
| join kind=inner secrets on AppObjectId
| where SecretTime between (ConsentTime .. ConsentTime + window)
// A different actor from the one who granted consent: that is the signal.
| where tolower(ConsentBy) != tolower(SecretBy)
| project ConsentTime, ConsentBy, SecretTime, SecretBy, AppName, AppObjectId
| order by SecretTime desc
```

## KQL — Defender XDR advanced hunting (CloudAppEvents)

<!-- query
platform: defender-xdr
name: Service principal credential changes recorded in cloud app activity
technique: T1098.001
severity: Medium
tactics: [Persistence, PrivilegeEscalation]
interval: PT1H
lookback: P30D
parameters: []
deployable: false
-->
```kql
// An adaptation of the hunting query published by Microsoft,
// "CredentialsAddAfterAdminConsentedToApp[Nobelium]". Entra audit events arrive in
// CloudAppEvents under Application "Office 365"; mind the full stop at the
// end of the ActionType values, which is present in Microsoft's own query too.
let lookback = 30d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Office 365"
| where ActionType startswith "Add service principal credentials"
     or ActionType startswith "Update application"
| where ActionType has_any ("service principal credentials", "Certificates and secrets")
| extend spnID = tostring(RawEventData.Target[3].ID)
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, spnID,
          IPAddress, UserAgent, IsAdminOperation, RawEventData
| order by Timestamp desc
```

Microsoft's original query filters with
`ActionType == "Add service principal credentials."` and
`ActionType == "Update application – Certificates and secrets management "`.
That second value contains an en dash and a trailing space. We use `startswith`
so as not to trip over that typography. Run
`CloudAppEvents | where Application == "Office 365" | distinct ActionType` to
establish which spelling your tenant produces.

## KQL — seeing the credential actually being used (AADServicePrincipalSignInLogs)

<!-- query
platform: sentinel
name: Service principal signs in with a credential key never seen before
technique: T1098.001
severity: Medium
tactics: [Persistence, PrivilegeEscalation]
interval: P1D
lookback: P30D
parameters: []
deployable: true
-->
```kql
// A new credential only becomes an incident once it is actually used.
// ServicePrincipalCredentialKeyId identifies the key the service principal
// signed in with; a key id that has not been seen before is the evidence.
let baseline = 30d;
let recent = 1d;
let known =
    AADServicePrincipalSignInLogs
    | where TimeGenerated between (ago(baseline) .. ago(recent))
    | distinct ServicePrincipalId, ServicePrincipalCredentialKeyId;
AADServicePrincipalSignInLogs
| where TimeGenerated > ago(recent)
| where ResultType == "0"
| join kind=leftanti known on ServicePrincipalId, ServicePrincipalCredentialKeyId
| project TimeGenerated, ServicePrincipalName, ServicePrincipalId, AppId,
          ServicePrincipalCredentialKeyId, ClientCredentialType, IPAddress,
          ResourceDisplayName, LocationDetails
| order by TimeGenerated desc
```

## Why this matters for BEC

A secret on a service principal is the form of persistence that survives a
password reset, an MFA reset and a session revocation alike, and that no longer
requires any user interaction. Microsoft describes exactly this step in the
responder guidance on the attack against its own corporate tenant
(25 January 2024): the actor *"created additional malicious OAuth
applications"*, also compromised an existing legacy test OAuth app with
elevated privileges, and used it *"to grant them the Office 365 Exchange Online
full_access_as_app role, which allows access to mailboxes"*.

For T1098.001 MITRE gives as procedure examples APT29, which during the
SolarWinds compromise added credentials to OAuth applications and service
principals, and Storm-0501, which reset administrator passwords without MFA and
then registered its own MFA method — the combination described in
[T1556.006](T1556.006-mfa-modification.md).

In SME-scale BEC the variant is often simpler: one app registration with
`Mail.Read`, a secret with a two-year lifetime, and a silent reader in the
executive mailbox.
