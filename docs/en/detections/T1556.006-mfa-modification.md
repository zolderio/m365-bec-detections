# T1556.006 — Modify Authentication Process: Multi-Factor Authentication

| | |
|---|---|
| **Name in the advisory** | Modify Authentication Process — adding an attacker-controlled MFA method to the victim's account |
| **Name in MITRE ATT&CK** | Modify Authentication Process: Multi-Factor Authentication |
| **MITRE tactic** | Persistence (TA0003), Credential Access (TA0006), Defense Impairment (TA0112, Defense Evasion in older versions) |
| **Advisory measure** | 009 — Restrict or disable OAuth app consent (priority High) |
| **Related technique** | [T1098.001](T1098.001-additional-cloud-credentials.md) — same measure, the app side |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> There is no alert for this. Not in Purview — there is no default alert policy
> for security info — and not in Entra ID Protection: the documented list of
> risk detections contains no detection at all for registering, deleting or
> downgrading an MFA method. The nearest detection
> `Suspicious MFA authentication approval` is about *approving* a prompt, not
> about registering a method, and it also requires Microsoft Entra ID P2. The
> events are, however, fully present in the Entra audit log and are cheap to
> alert on. This is the detection with the best effort-to-yield ratio in this
> entire cluster: build it, do not scope it too narrowly, and correlate it with
> the preceding sign-in.

## Is there a Defender alert for this?

**No.**

| | |
|---|---|
| **Purview alert policy** | None. The categories *Threat management*, *Permissions*, *Mail flow* and *Information governance* contain no policy that tracks security info registration. |
| **Entra ID Protection** | No risk detection for registering, changing or deleting an authentication method. |
| **Defender for Cloud Apps** | No anomaly detection policy for this action. |
| **What comes closest** | `Suspicious MFA authentication approval` (sign-in risk, real-time, riskEventType `authenticatorPhishing`, **Microsoft Entra ID P2**) and `User reported suspicious activity` (user risk, offline, riskEventType `userReportedSuspiciousActivity`, **P2**, and only if *Report suspicious activity* is enabled). Both concern the MFA prompt, not the registration. |

Without Entra ID P2 the only thing you see of the premium detections is
**`Additional risk detected`** without any detail; risk detections reporting is
*"Limited Information. No details drawer."* in P1 and absent altogether in Free.

So you have to build the alert yourself. The good side of that story: the audit
activities are stable and precisely documented.

## The audit activities (exact)

All six appear in the Entra audit reference under category **UserManagement**,
service **Authentication Methods**:

| Activity | What it means |
|---|---|
| `User registered security info` | The user has added a method themselves. This is the core event. |
| `User deleted security info` | A method has been removed. Attackers use this to lock out the legitimate user or to strip away a strong method. |
| `User changed default security info` | The default method has been shifted, for example from FIDO2 to SMS. Downgrade without anything being deleted. |
| `User started security info registration` | The run-up. Useful as an early signal and to see aborted attempts. |
| `User canceled security info registration` | Aborted registration. |
| `Admin registered security info` / `Admin deleted security info` / `Admin updated security info` | The same actions performed by an administrator — with a compromised admin account, the most severe variant. |

## Required data source

| Platform | Table | What must be onboarded |
|---|---|---|
| Microsoft Sentinel | `AuditLogs` | Data connector **Microsoft Entra ID**, log category **AuditLogs** ticked in the Entra ID diagnostic setting. |
| Microsoft Sentinel | `SigninLogs` | Same connector, log category **SignInLogs** ticked separately. Required for the correlation below. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps with the Microsoft 365 connector. **See the warning below.** |

This detection does **not** depend on measure 012 (Unified Audit Log): the Entra
audit log flows through diagnostic settings, not through the UAL.

**Not verified:** that the security info activities end up in `CloudAppEvents`.
What has been established is *that* Entra audit events land in that table under
`Application == "Office 365"` — Microsoft's own hunting query for
`Consent to application.` proves it. Whether the UserManagement activities
around security info are among them could not be confirmed from the Microsoft
documentation. The reliable route is `AuditLogs` in Sentinel. If you do want to
try it in Defender XDR, start with the inventory query at the bottom.

## KQL — Sentinel (AuditLogs): MFA method registered, deleted or downgraded

<!-- query
platform: sentinel
name: MFA method registered, deleted or changed
technique: T1556.006
severity: Medium
tactics: [Persistence, DefenseEvasion]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// The core rule. Deliberately broad: all mutations on security info, including
// the admin variants. In most tenants the volume of this is low enough to put
// an alert on it without tuning.
let lookback = 1d;
AuditLogs
| where TimeGenerated > ago(lookback)
| where Category == "UserManagement"
| where OperationName in (
    "User registered security info",
    "User deleted security info",
    "User changed default security info",
    "Admin registered security info",
    "Admin deleted security info",
    "Admin updated security info")
| where Result == "success"
| extend Actor              = tostring(InitiatedBy.user.userPrincipalName)
| extend ActorIP            = tostring(InitiatedBy.user.ipAddress)
| extend TargetUser         = tostring(TargetResources[0].userPrincipalName)
// The method type (Microsoft Authenticator, SMS, phone, FIDO2) sits in the free
// text of AdditionalDetails; the key name differs per activity, so it is
// deliberately not hard-parsed here but passed along for assessment.
| extend Details            = tostring(AdditionalDetails)
| extend AdminActionOnOther = tolower(Actor) != tolower(TargetUser)
| project TimeGenerated, OperationName, Actor, ActorIP, TargetUser,
          AdminActionOnOther, Details, CorrelationId
| order by TimeGenerated desc
```

## KQL — Sentinel: registration shortly after a sign-in from a new IP

<!-- query
platform: sentinel
name: MFA method registered within an hour of a sign-in from an unseen IP address
technique: T1556.006
severity: High
tactics: [Persistence, CredentialAccess]
interval: P1D
lookback: P14D
parameters: []
deployable: true
-->
```kql
// This is the rule you really want. An MFA registration on its own is
// commonplace (new phone). An MFA registration within an hour of a successful
// sign-in from an IP address this user has never used in the past 30 days is
// the AiTM pattern.
let baseline = 30d;
let window   = 1h;
let recent   = 7d;
let knownIPs =
    SigninLogs
    | where TimeGenerated between (ago(baseline) .. ago(recent))
    | where ResultType == "0"
    | distinct UserPrincipalName, IPAddress;
let newSignIns =
    SigninLogs
    | where TimeGenerated > ago(recent)
    | where ResultType == "0"
    | join kind=leftanti knownIPs on UserPrincipalName, IPAddress
    | project SignInTime = TimeGenerated, UserPrincipalName, IPAddress,
              Country = tostring(LocationDetails.countryOrRegion),
              AppDisplayName, UserAgent;
AuditLogs
| where TimeGenerated > ago(recent)
| where Category == "UserManagement"
| where OperationName in ("User registered security info",
                          "User deleted security info",
                          "User changed default security info")
| where Result == "success"
| extend UserPrincipalName = tostring(InitiatedBy.user.userPrincipalName)
| join kind=inner newSignIns on UserPrincipalName
| where TimeGenerated between (SignInTime .. SignInTime + window)
| project RegistrationTime = TimeGenerated, OperationName, UserPrincipalName,
          SignInTime, IPAddress, Country, AppDisplayName, UserAgent
| order by RegistrationTime desc
```

## KQL — Sentinel: strong method removed, weak method added

<!-- query
platform: sentinel
name: MFA method removed and a new one registered within 24 hours
technique: T1556.006
severity: Medium
tactics: [Persistence, DefenseEvasion]
interval: P1D
lookback: P14D
parameters: []
deployable: true
-->
```kql
// Downgrade within 24 hours: first delete something or shift the default, then
// register something new. This also happens with a genuine phone swap, so this
// is a prioritisation rule and not proof.
let window = 24h;
let changes =
    AuditLogs
    | where TimeGenerated > ago(14d)
    | where Category == "UserManagement"
    | where OperationName has "security info"
    | where Result == "success"
    | extend User = tostring(InitiatedBy.user.userPrincipalName)
    | extend IP = tostring(InitiatedBy.user.ipAddress);
changes
| where OperationName in ("User deleted security info", "User changed default security info")
| project DeleteTime = TimeGenerated, User, DeleteIP = IP, FirstAction = OperationName
| join kind=inner (
    changes
    | where OperationName == "User registered security info"
    | project RegistrationTime = TimeGenerated, User, RegistrationIP = IP
  ) on User
| where RegistrationTime between (DeleteTime .. DeleteTime + window)
| project User, FirstAction, DeleteTime, DeleteIP, RegistrationTime, RegistrationIP
| order by RegistrationTime desc
```

## KQL — Defender XDR advanced hunting (CloudAppEvents), with a caveat

<!-- query
platform: defender-xdr
name: Inventory of security info action types in the cloud app audit trail
technique: T1556.006
severity: Informational
tactics: [Persistence]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// First establish whether the activities are present in this table in your
// tenant. Run this inventory before building on the second query.
CloudAppEvents
| where Timestamp > ago(7d)
| where Application == "Office 365"
| where ActionType has "security info"
| distinct ActionType
```

<!-- query
platform: defender-xdr
name: Security info changes in the cloud app audit trail
technique: T1556.006
severity: Medium
tactics: [Persistence]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// If the previous query returns results, this is the detection.
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Office 365"
| where ActionType has "security info"
| project Timestamp, ActionType, AccountDisplayName, AccountObjectId, IPAddress,
          CountryCode, City, Isp, UserAgent, IsAdminOperation, RawEventData
| order by Timestamp desc
```

## Why this matters for BEC

Registering your own MFA method is the cheapest persistence there is: no
malware, no app, no code — just the *My Sign-Ins* portal that the compromised
user has access to themselves. It survives a password reset, and it turns a
stolen session token into permanent access.

For T1556.006 MITRE names **Scattered Spider** as an explicit procedure example,
which *"registers their own MFA tokens after account compromise"*, and for
[T1098.001](T1098.001-additional-cloud-credentials.md) **Storm-0501**, which
resets administrator passwords without MFA and then registers its own MFA
method.

Expel describes the action in the AiTM/BEC context and points to the same audit
event: *"Attackers will register their own MFA devices as a form of persistence.
Why? Their session token won't be valid forever."* — and, as a detection:
*"look for the 'User registered security info' event to detect when a user
registers a new MFA method."*

This is also why measure 004 (phishing-resistant MFA) only works if you monitor
measure 009 alongside it: an attacker who is allowed to register their own
Authenticator does not need the victim's FIDO2 key.
