# T1566.002 — Spearphishing Link

| | |
|---|---|
| **MITRE tactic** | Initial Access |
| **Advisory measures** | 004 — Phishing-resistant multi-factor authentication (priority High)<br>005 — Microsoft Defender for Office 365 (priority Medium) |
| **Related techniques** | [T1557](T1557-adversary-in-the-middle.md) — where the link usually leads<br>[T1598](T1598-phishing-for-information.md) — the same mail flow, but without a payload |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `DEFENDER-ALERT + SENTINEL-RULE` — both
>
> This is the technique Microsoft provides the best default coverage for:
> `A potentially malicious URL click was detected` and
> `A user clicked through to a potentially malicious URL` are both **High** and
> both trigger automated investigation. Switch them on. But both require E5/G5
> or the Defender for Office 365 Plan 2 add-on, both only work with Safe Links,
> and both depend on a *verdict*: the URL must have been recognised as
> malicious. An AiTM proxy on a domain that is an hour old does not have that
> verdict yet, and that is precisely the case that matters in BEC. The Sentinel
> rule covers the click without a verdict.

## Is there a Defender alert for this?

**Yes, two — and this time at a level someone actually looks at.**

| | |
|---|---|
| **Alert policy** | `A potentially malicious URL click was detected` |
| **Default severity** | **High** |
| **Licensing** | E5/G5 or Defender for Office 365 Plan 2 add-on |
| **What it is** | Fires when a user protected by Safe Links clicks a malicious link and that produces a *URL verdict change*. It also looks back 48 hours from the moment the verdict changes, and still generates alerts for clicks within that window. Triggers AIR automatically in Defender for Office 365 Plan 2. |
| **Limitation** | No verdict, no alert. Freshly registered phishing infrastructure escapes it until the verdict is there. |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

| | |
|---|---|
| **Alert policy** | `A user clicked through to a potentially malicious URL` |
| **Default severity** | **High** |
| **Licensing** | E5/G5 or Defender for Office 365 Plan 2 add-on |
| **What it is** | Fires when the user dismisses the Safe Links warning page with *Continue anyway* and opens the URL after all. |
| **Limitation** | Only on an explicit click-through; and only if the anti-phishing policy shows the warning page. |

Two policies that follow close behind, at a lower level:

| Alert policy | Severity | Licensing | Role |
|---|---|---|---|
| `Email messages containing malicious URL removed after delivery` | **Informational** | E3/G3, Microsoft 365 Business Premium, MDO Plan 1 add-on, E5/G5, or MDO Plan 2 add-on | ZAP removed the message after the fact. Useful, but `Informational`. Raising it is not demonstrably possible for a System policy — see [severity of a built-in policy](../index.md#can-you-raise-the-severity-of-a-built-in-policy). |
| `Messages containing malicious entity not removed after delivery` | **Medium** | same | ZAP tried and it failed. This is the more serious of the two and it still ranks lower than the clicks. |

Note: `Email messages containing phish URLs removed after delivery` still
exists, but Microsoft has replaced that policy with
`Email messages containing malicious URL removed after delivery` and advises
switching the old one off. Do not build anything new on it.

**A precondition, not a detail.** Safe Links is part of Defender for Office 365
Plan 1; advanced hunting on `UrlClickEvents` is part of Plan 2. With EOP alone
there is neither an alert nor a table.

## Required data source

| Platform | Table | What must be onboarded |
|---|---|---|
| Microsoft Sentinel | `UrlClickEvents`, `EmailEvents` | Data connector **Microsoft Defender XDR**, *Connect events* → tick the Defender for Office 365 tables. |
| Defender XDR advanced hunting | `UrlClickEvents`, `EmailEvents` | Defender for Office 365 rolled out; **advanced hunting requires Plan 2**. Safe Links must be enabled, otherwise `UrlClickEvents` stays empty. |

Not dependent on measure 012 (UAL).

One pitfall when linking a click to a message: for clicks on mail in Drafts and
Sent Items the email metadata is absent or `NetworkMessageId` is given a default
value. Those records therefore **cannot** be joined to `EmailEvents` on
`NetworkMessageId`.

## KQL — the click without a verdict (both platforms)

`UrlClickEvents` has the same column names in Sentinel and in advanced hunting.

<!-- query
platform: both
name: Safe Links click with no threat verdict on first-contact mail from an external sender
technique: T1566.002
severity: Medium
tactics: [InitialAccess]
interval: PT1H
lookback: P7D
parameters: [ownDomains]
deployable: true
-->

```kql
// Clicks where the filter stack saw no threat at the moment of clicking. This
// is exactly the set that produces no Defender alert at all. The filter on
// first contact and on an external sender turns it into something usable: the
// combination "unknown sender + click on a link" is the entry point of
// virtually every AiTM campaign.
let lookback = 7d;
let ownDomains = dynamic(["yourdomain.example", "yourseconddomain.example"]);   // <-- adjust
let firstContact =
    EmailEvents
    | where Timestamp > ago(lookback)
    | where EmailDirection == "Inbound"
    | where IsFirstContact == 1
    | where SenderFromDomain !in~ (ownDomains)
    | project NetworkMessageId, SenderFromAddress, SenderFromDomain, Subject,
              EmailDeliveryAction = DeliveryAction;
UrlClickEvents
| where Timestamp > ago(lookback)
| where Workload == "Email"
| where isempty(ThreatTypes)          // no verdict at the moment of clicking
| join kind=inner firstContact on NetworkMessageId
| project Timestamp, AccountUpn, Url, UrlChain, ActionType, IsClickedThrough,
          SenderFromAddress, SenderFromDomain, Subject, EmailDeliveryAction,
          IPAddress, NetworkMessageId, ReportId
| order by Timestamp desc
```

### Clicked through despite the warning

The query below appears verbatim in the Microsoft documentation of the table.

<!-- query
platform: both
name: User clicked through the Safe Links warning page to a phishing URL
technique: T1566.002
severity: High
tactics: [InitialAccess]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->

```kql
// Search for malicious links where user was allowed to proceed through
UrlClickEvents
| where ActionType == "ClickAllowed" or IsClickedThrough !="0"
| where ThreatTypes has "Phish"
| summarize by ReportId, IsClickedThrough, AccountUpn, NetworkMessageId, ThreatTypes, Timestamp
```

The complete list of `ActionType` values is **not in the schema
documentation**; `ClickAllowed` is the only value Microsoft names there.
Establish the rest with the built-in schema reference in the Defender portal
before filtering on them.

### Multiple recipients, the same URL

Targeted phishing rarely arrives in a single copy. This query looks for the
campaign instead of the message.

<!-- query
platform: both
name: Same URL clicked by multiple recipients within one week
technique: T1566.002
severity: Medium
tactics: [InitialAccess]
interval: PT1H
lookback: P7D
parameters: []
deployable: true
-->

```kql
let lookback = 7d;
UrlClickEvents
| where Timestamp > ago(lookback)
| where Workload == "Email"
| summarize Clicks         = count(),
            Clickers       = dcount(AccountUpn),
            Who            = make_set(AccountUpn, 30),
            ClickedThrough = countif(IsClickedThrough),
            First          = min(Timestamp),
            Last           = max(Timestamp)
          by Url
| where Clickers >= 3
| order by Clickers desc
```

### The delivered messages nobody clicked

A blind spot when cleaning up after a campaign: the messages that were delivered
but have not (yet) been clicked.

<!-- query
platform: both
name: Phishing mail delivered to the inbox that nobody clicked yet
technique: T1566.002
severity: Medium
tactics: [InitialAccess]
interval: PT1H
lookback: P7D
parameters: []
deployable: true
-->

```kql
let lookback = 7d;
let clicked = UrlClickEvents | where Timestamp > ago(lookback) | distinct NetworkMessageId;
EmailEvents
| where Timestamp > ago(lookback)
| where EmailDirection == "Inbound"
| where ThreatTypes has "Phish"
| where DeliveryLocation == "Inbox/Folder"    // delivered, despite the verdict
| where NetworkMessageId !in (clicked)
| project Timestamp, RecipientEmailAddress, SenderFromAddress, Subject,
          ThreatTypes, DetectionMethods, LatestDeliveryLocation, NetworkMessageId
| order by Timestamp desc
```

`LatestDeliveryLocation` is not available through the Streaming API and may
therefore be empty in Sentinel; in advanced hunting the column does work.

## Why this matters for BEC

In BEC the spearphishing link is almost never the goal but the hinge: it
delivers the credentials and the session cookie that open the mailbox. In June
2023 Microsoft described a campaign in which the link sat on a legitimate Canva
platform, redirected to a fake Microsoft sign-in page on Tencent cloud, and the
attacker signed in hours later with the stolen cookie from US IP addresses,
registered their own MFA method, created an inbox rule and then sent more than
16,000 phishing emails to the victim's contacts. MITRE places T1566.002 in
Initial Access; in this advisory it is the hinge phase between Credential Access
and everything that happens in the mailbox afterwards.
