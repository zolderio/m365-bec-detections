# T1114.002 — Remote Email Collection

| | |
|---|---|
| **MITRE tactic** | Collection |
| **Advisory measures** | 016 — Blocking automatic email forwarding (priority High)<br>017 — Restricting Teams & SharePoint collaboration (priority Medium) |
| **Related technique** | [T1114.003](T1114.003-email-forwarding-rule.md) — the rule; this file is about the reading itself |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> There is no alert policy that fires when somebody reads mail.
> `MailItemsAccessed` is an audit event, not a detection: it never produces an
> alert of its own accord. Granting mailbox delegation
> (`Add-MailboxPermission`, `Add-RecipientPermission`) has no default alert
> either — the only policy in the *Permissions* category is
> `Elevation of Exchange admin privilege` (severity **Low**), and that one is
> about role groups, not about mailbox permissions. Anyone who wants to see an
> attacker reading along has to build it themselves.

## Is there a Defender alert for this?

**No.** For the action itself (reading mail) no alert policy exists. Two things
come close, and here is why they do not close the gap:

| | |
|---|---|
| **Alert policy** | `Elevation of Exchange admin privilege` |
| **Default severity** | **Low** |
| **Licensing** | E1/F1/G1, E3/F3/G3 or E5/G5 |
| **Why it is not enough** | Microsoft: *"Generates an alert when someone is assigned administrative permissions in your Exchange Online organization."* That is the Organization Management role group — not `Add-MailboxPermission` on a single mailbox, which is precisely the quiet variant. |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

| | |
|---|---|
| **Mechanism** | Defender XDR automatic attack disruption |
| **What it is** | Incident level, not an alert policy. Microsoft gives as an example of an incident title: *"BEC financial fraud attack launched from a compromised account (attack disruption)"*. |
| **Why it is not enough** | It requires an E5-class subscription (or separate Defender plans) and a deployed Defender suite, and it only fires once the correlation recognises an attack in progress — not the first time somebody reads out a mailbox. See [T1657](T1657-financial-theft.md). |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/automatic-attack-disruption |

Relevant nonetheless: Microsoft explicitly names `MailItemsAccessed` as one of
the mailbox audit events that must be enabled for attack disruption in Defender
for Office 365 to work (*"At minimum, audit these mailbox events:
MailItemsAccessed, UpdateInboxRules, MoveToDeletedItems, SoftDelete, and
HardDelete"*).
Source: https://learn.microsoft.com/en-us/defender-xdr/configure-attack-disruption

## Licensing level

**`MailItemsAccessed` is part of Audit (Standard) and is on by default with
E3.** The older "E5 only" framing is no longer correct.

| | |
|---|---|
| **Microsoft Learn (verified 22 Aug 2026)** | *"The MailItemsAccessed action is part of Audit (Standard) functionality. It's part of Exchange mailbox auditing and is enabled by default for users that are assigned an Office 365 E3/E5 or Microsoft 365 E3/E5 license."* |
| **Source** | https://learn.microsoft.com/en-us/purview/audit-log-investigate-accounts (ms.date 2026-06-19) |
| **Confirmation** | In the table of mailbox actions, `MailItemsAccessed` is listed with a ✔\* (= logged by default) for Admin, Delegate and Owner alike, with no licensing footnote. The only action that does carry such a footnote is `MessageBind` ("available only for users *without* E5/A5/G5 licenses"). Source: https://learn.microsoft.com/en-us/purview/audit-mailboxes |

**Two places where the documentation contradicts itself — mention these if you
end up in a licensing discussion:**

1. Microsoft's own page *Investigate shared mailbox activities using audit
   logs* still says of the same event: *"This command requires Microsoft 365 E5
   licensing to capture `MailItemsAccessed` operations."* That is out of date.
   Source: https://learn.microsoft.com/en-us/purview/audit-log-identify-mailboxes
2. CISA AA23-193A (July 2023) advises *"Enable Purview Audit (Premium)
   logging. This logging requires licensing at the G5/E5 level."* That was
   correct when the advisory was published, but no longer holds for this
   specific event. The substantive point of that advisory does still stand (see
   *Why this matters for BEC*).

Note: `SearchQueryInitiated` — the event that records what the attacker was
searching for in the mailbox — is **not** on by default and must be enabled per
mailbox (`Set-Mailbox <identity> -AuditOwner @{Add="SearchQueryInitiated"}`).
Source: CISA, *Microsoft Expanded Cloud Logs Implementation Playbook* (May 2026).

## Four properties of MailItemsAccessed you need to know

Without these four you will read the results incorrectly.

**1. Bind versus Sync.** The access type is in the field `MailAccessType`
within `OperationProperties`.

| Value | What it means | What to do with it |
|---|---|---|
| `Bind` | One specific message was opened. The `InternetMessageId` of each message is in the record. | You know exactly which mail was read. |
| `Sync` | A client synchronised an entire folder. It contains no information about individual messages. | **Treat the whole folder as compromised.** Microsoft: *"All mail items in the synced folder are assumed to be compromised."* |

Sync operations are only recorded for the desktop version of Outlook for
Windows or Mac. If the attacker synchronised, they can read offline afterwards
without anything further being logged.

**2. Bind operations are aggregated.** All bind operations within a window of
**2 minutes** are combined into a single audit record, in the field `Folders`
within `AuditData`. The number of aggregated operations is in `OperationCount`.
One record is therefore not one mail read.

**3. Duplicates are filtered out.** Microsoft filters duplicate bind operations
for the same `InternetMessageId` within **one hour**, and sync operations at
hourly intervals. Exception: if one of `ClientIPAddress`, `ClientInfoString`,
`ParentFolder`, `Logon_type`, `MailAccessType`, `MailboxUPN`, `User` or
`SessionId` differs, a new record is created after all. That is exactly why an
attacker with a different IP or a different client remains visible alongside
the ordinary user.

**4. Throttling — and what the documentation does and does not say.**

| | |
|---|---|
| **The claim** | More than 1,000 `MailItemsAccessed` records on one mailbox within 24 hours → Exchange Online stops logging for 24 hours; recognisable by the field `IsThrottled`. |
| **Found** | CISA, *Microsoft Expanded Cloud Logs Implementation Playbook* (updated May 2026), published jointly with Microsoft: *"MailItemsAccessed events can be throttled if more than 1,000 records are generated on a mailbox in less than 24 hours. When this occurs, MailItemsAccessed activity will not be logged for 24 hours after the mailbox was throttled."* It also states there: throttling does not apply when an admin searches *other* mailboxes, fewer than one per cent of all mailboxes in Exchange Online are throttled, and *"the presence of throttling could be an indication of mailbox misuse or compromise"*. The field `IsThrottled` is named in the same list. |
| **Also found** | Microsoft's own hunting repo on GitHub, query *MailItemsAccessed Throttling [Nobelium]*, with the same 1,000-in-24-hours wording and a KQL that tests on `RawEventData['OperationProperties'][1]`. |
| **Not found** | On the current Microsoft Learn pages there is **nothing** to be found about throttling or `IsThrottled`: not on *Use MailItemsAccessed to investigate compromised accounts* (ms.date 2026-06-19) and not on *Learn about properties in Exchange audit records* (ms.date 2026-06-19), which does list `Folders`, `FolderItems`, `OperationCount` and `SessionId`. A targeted search within learn.microsoft.com for `IsThrottled` likewise returns no page describing the field. |
| **Conclusion** | The behaviour is confirmed by two authoritative sources co-published with Microsoft, one of them from May 2026. It is **not** confirmed in the current product documentation. Treat the exact threshold of 1,000 as not guaranteed and build the detection on the presence of `IsThrottled`, not on counting to 1,000 yourself. |

The practical consequence is unforgiving: with an attacker who reads a lot,
your evidence disappears at precisely the moment it matters. A record with
`IsThrottled` is therefore not noise but one of the strongest signals in this
entire file.

## KQL — Sentinel (OfficeActivity)

<!-- query
platform: sentinel
name: Mailbox items accessed, with access type and throttling flag
technique: T1114.002
severity: Informational
tactics: [Collection]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// Mail access with the access type and the throttling flag pulled out.
// MailAccessType and IsThrottled sit as Name/Value pairs in
// OperationProperties; extract() is used deliberately instead of a
// positional index, because the ordering of that array is not documented.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation =~ "MailItemsAccessed"
| extend OpProps        = tostring(OperationProperties)
| extend MailAccessType = extract(@'"Name"\s*:\s*"MailAccessType"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, OpProps)
| extend IsThrottled    = extract(@'"Name"\s*:\s*"IsThrottled"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, OpProps)
| project TimeGenerated, UserId, MailboxOwnerUPN, Logon_Type, MailAccessType, IsThrottled,
          ClientIP, ClientInfoString, ClientAppId, AppId, Folders, OperationProperties
| order by TimeGenerated desc
```

Three filters to put on top of it, in order of yield:

<!-- query
platform: sentinel
name: Throttled, synchronised or non-owner mailbox access
technique: T1114.002
severity: Medium
tactics: [Collection]
interval: PT1H
lookback: P1D
parameters: []
deployable: false
-->
```kql
// (a) Throttling: the log has stopped. Always investigate.
| where IsThrottled =~ "True"

// (b) Sync: the whole folder is gone. It does not say which messages.
| where MailAccessType =~ "Sync"

// (c) Access by somebody other than the owner (Delegate = 2, Admin = 1).
| where Logon_Type !in ("0", "Owner")
```

## KQL — Defender XDR advanced hunting (CloudAppEvents)

<!-- query
platform: defender-xdr
name: Mailbox items accessed, seen in cloud app activity
technique: T1114.002
severity: Informational
tactics: [Collection]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where ActionType == "MailItemsAccessed"
| extend OpProps        = tostring(RawEventData.OperationProperties)
| extend MailAccessType = extract(@'"Name":"MailAccessType","Value":"([^"]+)"', 1, OpProps)
| extend IsThrottled    = extract(@'"Name":"IsThrottled","Value":"([^"]+)"', 1, OpProps)
| extend AccessingAppId = tostring(RawEventData.AppId)
| extend ClientInfo     = tostring(RawEventData.ClientInfoString)
| extend MailboxSession = tostring(RawEventData.SessionId)
| extend MailboxUPN     = tostring(RawEventData.MailboxOwnerUPN)
| project Timestamp, AccountDisplayName, AccountObjectId, MailboxUPN, IPAddress,
          MailAccessType, IsThrottled, AccessingAppId, ClientInfo, MailboxSession
| order by Timestamp desc
```

## Hunting heuristics from the CISA playbook

The CISA playbook (May 2026) offers two usable methods. Both are included in
this file because they do not rely on an alert.

**First time an AppId accesses a mailbox.** Trend the number of mail accesses
per application over time; a spike or an unknown application is the signal.
CISA's variant, lightly adapted so that the new AppIds come out by themselves
instead of you having to read a graph:

<!-- query
platform: defender-xdr
name: Application accesses a mailbox for the first time
technique: T1114.002
severity: Medium
tactics: [Collection]
interval: P1D
lookback: P30D
parameters: []
deployable: false
-->
```kql
// Defender XDR — AppIds accessing a mailbox for the first time in the last 24
// hours, measured against the preceding 29 days.
let baseline = CloudAppEvents
    | where Timestamp between (ago(30d) .. ago(1d))
    | where ActionType == "MailItemsAccessed"
    | distinct AppId = tostring(RawEventData.AppId);
CloudAppEvents
| where Timestamp > ago(1d)
| where ActionType == "MailItemsAccessed"
| extend AppId = tostring(RawEventData.AppId)
| where AppId !in (baseline)
| summarize Mailboxes = dcount(AccountObjectId), Events = count(),
            Example = any(tostring(RawEventData.ClientInfoString)) by AppId
| order by Mailboxes desc
```

The unmodified CISA version, for those who prefer to look at a timechart:

<!-- query
platform: defender-xdr
name: Trend of mailbox access volume per accessing application
technique: T1114.002
severity: Informational
tactics: [Collection]
interval: P1D
lookback: P30D
parameters: []
deployable: false
-->
```kql
CloudAppEvents
| where ActionType == "MailItemsAccessed"
| extend Accessing_AppId = tostring(RawEventData.AppId)
| summarize count() by bin(Timestamp,1d), Accessing_AppId
| render timechart
```

<!-- query
platform: sentinel
name: Trend of mailbox access volume per application in the unified audit log
technique: T1114.002
severity: Informational
tactics: [Collection]
interval: P1D
lookback: P30D
parameters: []
deployable: false
-->
```kql
OfficeActivity
| where Operation == "MailItemsAccessed"
| summarize count() by bin(TimeGenerated,1d), AppId
| render timechart
```

**Pivoting on SessionId.** `SessionId` is a GUID in the Entra token and only
changes when the user authenticates again. It lets you group everything that
happened within one logon session, independently of IP address and user agent —
which an attacker changes without effort. Reactive, when you have one
suspicious IP:

<!-- query
platform: defender-xdr
name: Mail read in sign-in sessions from a suspicious IP address
technique: T1114.002
severity: High
tactics: [Collection]
interval: P1D
lookback: P7D
parameters: [suspiciousIp]
deployable: false
-->
```kql
// Defender XDR — which mail was read in the sessions from a suspicious IP.
// EntraIdSignInEvents requires Entra ID P2. Until 19 Oct 2026 this table is
// also still called AADSignInEventsBeta; it is then migrated automatically.
let suspiciousIp = "x.x.x.x";          // <-- adjust
let bad_sessions = materialize (
    EntraIdSignInEvents
    | where IPAddress == suspiciousIp
    | where isnotempty(SessionId)
    | distinct SessionId
);
CloudAppEvents
| where ActionType == "MailItemsAccessed"
| where tostring(RawEventData.SessionId) in (bad_sessions)
| project Timestamp, AccountDisplayName, IPAddress,
          MailAccessType = tostring(RawEventData.OperationProperties),
          Folders = RawEventData.Folders
```

## Mailbox delegation: the quiet way of reading along

An attacker who does not want every session to be visible on the victim's
account grants themselves permissions on the mailbox and reads on from their
own account. That survives a password change, just as a forwarding rule does.
The actions, and what the audit says about them:

| Action | What it grants | Documented as an audit activity? |
|---|---|---|
| `Add-MailboxPermission` | FullAccess on somebody else's mailbox | **Yes.** Microsoft: *"An administrator assigned the FullAccess mailbox permission to a user (known as a delegate) to another person's mailbox."* |
| `Remove-MailboxPermission` | Revoking those same permissions — an attacker cleaning up | **Yes**, with its own description. |
| `Add-RecipientPermission` | Send-As: sending messages that appear to come from the mailbox owner | **Not found as a separate entry** on the activities page. The cmdlet itself is documented (*"Use the Add-RecipientPermission cmdlet to add SendAs permission"*, the only valid `-AccessRights` is `SendAs`) and Exchange admin cmdlets appear in the audit log as `RecordType` **ExchangeAdmin** with the parameters used in `Parameters`. So filter on it, but be aware that the coverage is not explicitly documented. |
| `Set-Mailbox -GrantSendOnBehalfTo` | Send-on-behalf | Likewise: `Set-Mailbox` is a documented audit operation for mailbox settings; the specific parameter is in `Parameters`. |
| `UpdateFolderPermissions` | Permissions on a single folder, for example only the Inbox | **Yes**, and logged by default (✔\*) for Admin, Delegate and Owner alike. Microsoft notes that `AddFolderPermissions`, `ModifyFolderPermissions` and `RemoveFolderPermissions` are included in it and are not logged separately — do not use those values. |

<!-- query
platform: sentinel
name: Mailbox permission, Send-As or Send-on-behalf granted
technique: T1114.002
severity: Medium
tactics: [Collection, Persistence]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// Sentinel — granting of mailbox permissions, Send-As, Send-on-behalf and
// folder permissions in a single rule. Set-Mailbox is deliberately filtered on parameter,
// otherwise it fires on every mailbox change.
let lookback = 7d;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation in~ ("Add-MailboxPermission", "Remove-MailboxPermission",
                       "Add-RecipientPermission", "Remove-RecipientPermission",
                       "Set-Mailbox", "UpdateFolderPermissions")
| extend Params = tostring(Parameters)
| where Operation !~ "Set-Mailbox" or Params has "GrantSendOnBehalfTo"
| extend Trustee     = extract(@'"Name"\s*:\s*"(?:Trustee|User)"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, Params)
| extend AccessRight = extract(@'"Name"\s*:\s*"AccessRights"\s*,\s*"Value"\s*:\s*"([^"]+)"', 1, Params)
| project TimeGenerated, UserId, Operation, MailboxOwnerUPN, Trustee, AccessRight,
          ClientIP, ExternalAccess, ResultStatus, Params
| order by TimeGenerated desc
```

<!-- query
platform: defender-xdr
name: Mailbox permission changes recorded in cloud app activity
technique: T1114.002
severity: Medium
tactics: [Collection, Persistence]
interval: PT1H
lookback: P1D
parameters: []
deployable: false
-->
```kql
// Defender XDR — the same actions.
let lookback = 7d;
CloudAppEvents
| where Timestamp > ago(lookback)
| where ActionType in~ ("Add-MailboxPermission", "Remove-MailboxPermission",
                        "Add-RecipientPermission", "Remove-RecipientPermission",
                        "Set-Mailbox", "UpdateFolderPermissions")
| extend Params = tostring(RawEventData.Parameters)
| where ActionType !~ "Set-Mailbox" or Params has "GrantSendOnBehalfTo"
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, IPAddress,
          Mailbox = tostring(RawEventData.MailboxOwnerUPN), Params
| order by Timestamp desc
```

A useful refinement during an ongoing investigation: `FolderBind` records that
a delegate opens a folder, but is **not** on by default and does not log the
owner. It can be enabled per mailbox with
`Set-Mailbox <mailbox> -AuditDelegate @{Add="FolderBind"}`. Microsoft
consolidates those records: one record per folder per 24 hours.

## Why this matters for BEC

For BEC this is the event that determines whether you can say anything
afterwards. An attacker who wants to imitate the invoice flow must first read
who talks to whom about money. CISA and the FBI wrote in AA23-193A (12 July
2023) about a federal organisation that noticed a breach of Exchange Online
solely through `MailItemsAccessed` records with an unexpected `ClientAppID` and
`AppID`, and concluded verbatim: *"CISA and FBI are not aware of other audit
logs or events that would have detected this activity."*

That makes this the only event with which you can establish after the fact
which mail an attacker has read — and therefore whether you have a notification
obligation. With `Sync` you cannot do that per message: then it is the whole
folder. And with throttling you cannot do it at all for 24 hours.

The scale involved: in 2025 the FBI received 24,768 BEC reports with reported
losses of $3,046,598,558 (IC3 Annual Report 2025), against 21,442 reports and
$2,770,151,146 in 2024.
