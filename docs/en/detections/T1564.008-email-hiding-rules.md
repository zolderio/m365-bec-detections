# T1564.008 — Email Hiding Rules

| | |
|---|---|
| **MITRE tactic** | Stealth (ATT&CK v19.2; Defense Evasion in older versions) |
| **Advisory phase** | 08. Defense Evasion |
| **Advisory measures** | 011 — Forward security alerts (High) · 012 — Enable the Unified Audit Log (High) · 013 — Monitoring for configuration drift (High) |
| **Related technique** | [T1114.003](T1114.003-email-forwarding-rule.md) — same events, different purpose |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — there is no alert here, build it yourself
>
> There is **no** default alert policy that fires on an inbox rule that moves,
> deletes or marks mail as read. `Creation of forwarding/redirect rule` only
> covers forwarding and redirecting, and the Defender for Cloud Apps policy that
> filled this gap (*Suspicious inbox manipulation rules*) was switched off as of
> June 2025. Adjusting a severity therefore does not help here: there is nothing
> to raise. Microsoft's own shipped Sentinel rules do not cover it fully either
> — see below. This is the most important self-built detection in this entire
> cluster.

## Is there a Defender alert for this?

**No.** Microsoft's list of default alert policies has four categories
(Information governance, Mail flow, Permissions, Threat management) and none of
them contains a policy for the creation of a move, delete or mark-as-read rule.

The policy that comes closest explicitly does *not* cover it:

| | |
|---|---|
| **Alert policy** | `Creation of forwarding/redirect rule` |
| **Default severity** | **Informational** |
| **Licensing** | E1/F1/G1, E3/F3/G3 or E5/G5 — no add-on required |
| **Why it does not help** | Microsoft: *"Generates an alert when someone in your organization creates an inbox rule for their mailbox that forwards or redirects messages to another email account."* A rule that only moves, deletes or marks as read falls outside it. In addition: *"This policy only tracks inbox rules that are created using Outlook on the web (formerly known as Outlook Web App) or Exchange Online PowerShell."* |
| **Source** | https://learn.microsoft.com/en-us/defender-xdr/alert-policies |

**The coverage gap many organisations are unaware of.** Defender for Cloud Apps
had two anomaly policies that did fire on this. Microsoft switched them off as
of June 2025:

> *"Starting June 2025, Microsoft Defender for Cloud Apps began transitioning
> anomaly detection policies to a dynamic threat detection model. […] several
> legacy policies have been disabled: […] Suspicious inbox manipulation rules
> […] Suspicious email deletion activity […]"*

For *Suspicious inbox manipulation rules* it says only "disabled, migrated to
the new dynamic model" — no replacement policy name. The name of what takes its
place is therefore **not publicly documented**. If this policy is still in your
detection inventory as coverage for T1564.008, that coverage no longer exists.
Source: https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

**The shipped Sentinel rules do not close the gap either.** In the Azure Sentinel
repository Microsoft provides two analytic rules that appear to target this
behaviour. Both are severity `Medium` and both filter on the same three values:

| Rule | Solution | Operations | Destination filter |
|---|---|---|---|
| `Malicious Inbox Rule` (v2.0.4) | Microsoft 365 | `New-InboxRule` only | `Parameters has "Deleted Items" or "Junk Email" or "DeleteMessage"` |
| `Malicious BEC Inbox Rule` (v1.0.2) | Business Email Compromise - Financial Fraud | `New-InboxRule` only | same |

That means they miss three things that matter in practice:

1. **RSS Feeds, RSS Subscriptions, Conversation History, Notes and Archive** —
   precisely the folders that, according to Red Canary, are abused most often.
2. **`UpdateInboxRules`** — the operation written by the Outlook desktop client
   (Microsoft: *"Updated inbox rules from Outlook client"*). A rule created from
   the desktop client therefore produces no hit.
3. **`MarkAsRead` without a delete action** — the variant in which mail simply
   stays in the inbox but the unread counter does not go up.

Sources:
https://github.com/Azure/Azure-Sentinel/blob/master/Solutions/Microsoft%20365/Analytic%20Rules/Malicious_Inbox_Rule.yaml and
https://github.com/Azure/Azure-Sentinel/blob/master/Solutions/Business%20Email%20Compromise%20-%20Financial%20Fraud/Analytic%20Rules/BEC_MailboxRule.yaml

## KQL — Sentinel (OfficeActivity)

<!-- query
platform: sentinel
name: Inbox rule that hides mail instead of forwarding it
technique: T1564.008
severity: High
tactics: [DefenseEvasion]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// Inbox rule that hides mail away instead of forwarding it.
// Deliberately covers three things the shipped rules Malicious Inbox Rule and
// Malicious BEC Inbox Rule do NOT cover:
//   1. UpdateInboxRules  -> the operation of the Outlook desktop client;
//   2. destination folders beyond Deleted Items / Junk Email, in particular
//      RSS Feeds, RSS Subscriptions and Conversation History;
//   3. MarkAsRead as a signal in its own right, without a delete action.
let lookback = 1d;
// Folder names are logged as the client supplies them; include the Dutch
// variants if there are Dutch-language clients in the tenant.
let SuspiciousFolders = dynamic([
    "RSS Feeds", "RSS Subscriptions", "Conversation History", "Notes",
    "Archive", "Junk Email", "Deleted Items",
    "RSS-feeds", "RSS-abonnementen", "Gespreksgeschiedenis", "Notities",
    "Archief", "Ongewenste e-mail", "Verwijderde items"]);
let HidingActions = dynamic(["DeleteMessage", "MarkAsRead", "MoveToFolder", "StopProcessingRules"]);
// Financial keywords: these are what the attacker uses to filter away the payment correspondence.
let FinancialTerms = dynamic([
    "invoice", "factuur", "payment", "betaling", "betaal", "iban", "bank",
    "rekeningnummer", "remittance", "wire", "transfer", "overboeking",
    "purchase order", "inkooporder", "aanmaning", "incasso", "swift",
    "chargeback", "payroll", "salaris", "deposit", "ach "]);
// Alarm keywords: these are what the attacker uses to filter away the warnings.
let AlertTerms = dynamic([
    "phish", "spam", "hacked", "gehackt", "compromise", "gecompromitteerd",
    "suspicious", "verdacht", "malicious", "helpdesk", "password", "wachtwoord",
    "do not open", "niet openen", "virus", "scam", "postmaster", "mailer-daemon"]);
OfficeActivity
| where TimeGenerated > ago(lookback)
| where OfficeWorkload =~ "Exchange"
| where Operation in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
// UpdateInboxRules does not always populate ResultStatus; leave empty values in.
| where ResultStatus in~ ("True", "Succeeded") or isempty(ResultStatus)
| extend Params = tostring(Parameters)
| where Params has_any (HidingActions) or Params has_any (SuspiciousFolders)
// Which of the suspicious folders occurs in the rule?
| mv-apply Folder = SuspiciousFolders to typeof(string) on (
      summarize TargetFolders = make_set_if(Folder, Params contains Folder)
  )
| extend Deletes         = Params has "DeleteMessage"
| extend MarksAsRead     = Params has "MarkAsRead"
| extend FinancialFilter = Params has_any (FinancialTerms)
| extend AlertFilter     = Params has_any (AlertTerms)
| extend Score           =   iff(array_length(TargetFolders) > 0, 2, 0)
                           + iff(Deletes, 3, 0)
                           + iff(MarksAsRead, 1, 0)
                           + iff(FinancialFilter, 3, 0)
                           + iff(AlertFilter, 3, 0)
                           + iff(Operation =~ "UpdateInboxRules", 1, 0)
| where Score >= 4
| extend ClientIPAddress = case(ClientIP has ".", tostring(split(ClientIP, ":")[0]),
                                ClientIP has "[", tostring(trim_start(@'[[]', tostring(split(ClientIP, "]")[0]))),
                                ClientIP)
| project TimeGenerated, UserId, Operation, ClientIPAddress, TargetFolders,
          Deletes, MarksAsRead, FinancialFilter, AlertFilter, Score,
          ClientInfoString, OriginatingServer, Params
| order by Score desc, TimeGenerated desc
```

In practice the threshold `Score >= 4` means: a move to a suspicious folder plus
either a keyword filter or a delete action. Set it to `3` for a hunting run and
to `6` if the rule is allowed to open an incident autonomously.

## KQL — Defender XDR advanced hunting (CloudAppEvents)

<!-- query
platform: defender-xdr
name: Inbox rule with hiding actions in the cloud app audit trail
technique: T1564.008
severity: High
tactics: [DefenseEvasion]
interval: P1D
lookback: P7D
parameters: []
deployable: false
-->
```kql
// Same logic on CloudAppEvents. In its own alert grading playbook Microsoft
// uses RawEventData.Parameters for these operations, including
// UpdateInboxRules.
let lookback = 7d;
let SuspiciousFolders = dynamic([
    "RSS Feeds", "RSS Subscriptions", "Conversation History", "Notes",
    "Archive", "Junk Email", "Deleted Items"]);
let HidingActions = dynamic(["DeleteMessage", "MarkAsRead", "MoveToFolder", "StopProcessingRules"]);
let FinancialTerms = dynamic([
    "invoice", "factuur", "payment", "betaling", "iban", "bank", "remittance",
    "wire", "transfer", "purchase order", "incasso", "payroll", "deposit"]);
CloudAppEvents
| where Timestamp > ago(lookback)
| where Application == "Microsoft Exchange Online"
| where ActionType in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| extend Params = tostring(RawEventData.Parameters)
| where Params has_any (HidingActions) or Params has_any (SuspiciousFolders)
| extend Deletes         = Params has "DeleteMessage"
| extend MarksAsRead     = Params has "MarkAsRead"
| extend FinancialFilter = Params has_any (FinancialTerms)
| project Timestamp, AccountDisplayName, AccountObjectId, ActionType, IPAddress,
          CountryCode, City, UserAgent, Deletes, MarksAsRead,
          FinancialFilter, RuleConfig = Params
| order by Timestamp desc
```

## Sharpening: the rule name

Red Canary describes three recurring naming patterns for malicious inbox rules:
one or more punctuation marks (`.`, `,`, `;`, `-`, `=`, with examples such as
`.,.,..,` and `---`), a run of repeated characters (`a`, `aaa`, `QQ`,
`MMMMMMMMMMMMMMMMMMM`), and a word or abbreviation of 2–4 characters (`IT`,
`rule`, `mail`, `new`, `ACH`). A rule with no name at all, or with a
meaningless one, is a signal in itself.

<!-- query
platform: sentinel
name: Inbox rule with a missing or meaningless name
technique: T1564.008
severity: Medium
tactics: [DefenseEvasion]
interval: PT1H
lookback: P1D
parameters: []
deployable: false
-->
```kql
// Best-effort: pull the rule name out of Parameters. The exact serialisation of
// Parameters differs per operation and per client -- first check in your own
// tenant what a real New-InboxRule record looks like before alerting on this.
| extend RuleName = extract(@'"Name"\s*:\s*"Name"\s*,\s*"Value"\s*:\s*"([^"]*)"', 1, Params)
| extend SuspiciousName = isempty(RuleName)
                       or strlen(RuleName) <= 4
                       or RuleName matches regex @'^[\.\,\;\-\=\s]+$'
```

If you want one rule with a very low false-positive rate alongside the broader
query, this is it. Legitimate use of the RSS folders is zero in most
organisations.

## Why this matters for BEC

A hiding rule is not a by-product but the core of the fraud: it makes sure the
victim does not see the supplier's questions, the bank's confirmation and the IT
department's warning, while the attacker takes over the invoice correspondence.

- **Red Canary** places Email Hiding Rules at **#9** in the top 10 techniques of
  the 2026 Threat Detection Report: 8.3% of their customers affected, 428
  detected threats. They explicitly name the folders `Archive`,
  `Conversation History`, `Deleted Items`, `Junk Email`, `RSS Feeds` and
  `RSS Subscriptions`, with Conversation History, RSS Feeds and RSS
  Subscriptions as "frequently abused". The observed filter terms fall into two
  categories: security incident (`phish`, `hacked`, `compromised`,
  `suspicious`, `postmaster`, …) and money/finance/payroll (`ach`, `bank`,
  `bill payment verification`, `chargeback`, `deposit`, `direct deposit`,
  `payroll`, `vendor`, `void`). That second list is why the query above filters
  on financial keywords.
- **CISA** describes, from its own incident investigation, rules that move
  incoming warnings to the *RSS Subscriptions* folder so the victim does not see
  them (AR21-013A, January 2021).
- **Microsoft** itself, in the alert grading playbook: *"They might also set
  rules in the compromised user mailbox to delete emails, move the emails into
  another less noticeable folder (like RSS), or forward mails to an external
  account. Some rules might move all the emails to another folder and mark them
  as 'read'."* And: *"Mostly, a rule of 'delete all incoming emails' without
  filtering them with keywords is an indicator of malicious activity."*
- **FBI PIN 20201125-001** warned that rules created in the web client do not
  sync to the desktop client and therefore remain invisible to the
  administrator.
