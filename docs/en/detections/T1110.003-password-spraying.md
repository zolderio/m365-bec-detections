# T1110.003 — Password Spraying

| | |
|---|---|
| **MITRE tactic** | Credential Access |
| **Advisory measures** | 004 — Phishing-resistant multifactor authentication (priority High)<br>005 — Microsoft Defender for Office 365 (priority Medium) |
| **Related techniques** | [T1621](T1621-mfa-request-generation.md) — what happens after a successful spray<br>[T1078.004](T1078.004-cloud-accounts.md) — the use of the discovered password |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> Microsoft Entra ID Protection has a detection called literally **Password
> spray**, but it is unsuitable as sole coverage in two ways. It requires
> Microsoft Entra ID P2 — without P2 you only see *Additional risk detected*
> without any details — and according to Microsoft it only fires **after the
> attacker has successfully validated a password**: failed spray attempts
> against your users produce no detection. That makes it not an early warning
> but a compromise notification. The pattern you do see in time — one source,
> many accounts, one password attempt per account — you build yourself on the
> sign-in logs. If you have P2, put the Entra detection alongside it as a
> safety net.

## Is there a Defender alert for this?

**Partly, and only premium.** There is no default alert policy for sign-ins:
the policies in the Defender portal are about mail, files and administrative
actions, not about sign-ins. The coverage sits in Entra ID Protection and
Defender for Cloud Apps.

| | |
|---|---|
| **Risk detection** | `Password spray` (sign-in risk, `riskEventType` = `passwordSpray`) |
| **Detection type** | Real-time or offline |
| **Licensing** | **Microsoft Entra ID P2** |
| **Default severity** | Risk detections have a *risk level* (low/medium/high) rather than an alert severity. The fixed risk level of this detection is **not publicly documented**. |
| **Limitation (important)** | Microsoft: *"The risk detection is only triggered when an attacker successfully validates a user's password. Unsuccessful spray attempts against your users don't generate a detection."* |
| **Without P2** | `Additional risk detected` — Free or P1, without detection details |
| **Source** | https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks |

| | |
|---|---|
| **Detection** | Defender for Cloud Apps, `Multiple failed login attempts` |
| **Licensing** | Microsoft Defender for Cloud Apps (standalone, or M365 E5 with EMS E5) |
| **What it is** | Fires on multiple failed sign-ins within one session relative to the learned baseline. Works per user, not per source IP — a spray that makes one attempt per account usually falls outside it. |

**Retired, do not build on this any more.** The Defender for Cloud Apps policy
`Activity from suspicious IP addresses` — the policy that picked up
password-spray IPs — was turned off as a legacy policy in June 2025 and,
according to Microsoft, migrated to the dynamic model under the names
`Successful logon from a suspicious IP address` and `Activity from a
password-spray associated IP address`.
See https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

**What does not cover your cloud sign-ins.** Microsoft Defender for Identity
has `Suspected Brute Force attack (Kerberos, NTLM)`, and the description
mentions password spray explicitly. That detection runs on sensors on your
domain controllers and is about on-premises Active Directory, not about
sign-ins to Microsoft 365. Do not count it as coverage for this technique.

## Required data source

| Platform | Table | What needs to be onboarded |
|---|---|---|
| Microsoft Sentinel | `SigninLogs`, `AADNonInteractiveUserSignInLogs` | Data connector **Microsoft Entra ID**. Microsoft: *"A Microsoft Entra ID P1 or P2 license is required to ingest sign-in logs into Microsoft Sentinel."* |
| Microsoft Sentinel | `AADUserRiskEvents` | Same connector (log type *User risk events*). Detection details require Entra ID P2. |
| Defender XDR advanced hunting | `EntraIdSignInEvents` | **Entra ID P2** required to populate and read this table. |

**Mind the table migration.** `AADSignInEventsBeta` will be retired on
**19 October 2026** and replaced by `EntraIdSignInEvents`; the latter is
already available now and existing queries are migrated automatically. Write
new detections on `EntraIdSignInEvents`.

Not dependent on measure 012 (UAL) — sign-in logs come from Entra ID, not from
the Unified Audit Log.

## KQL — Sentinel (SigninLogs)

<!-- query
platform: sentinel
name: Single source failing password attempts against many distinct accounts
technique: T1110.003
severity: Medium
tactics: [CredentialAccess]
interval: PT1H
lookback: P1D
parameters: [minUsers]
deployable: true
-->
```kql
// Spray pattern: one source hits many different accounts with the same
// error 50126 (InvalidUserNameOrPassword) every time. Deliberately NO filter on the
// number of attempts per account - that is precisely the difference from brute force:
// with spraying there are only one or two, which is why smart lockout does not kick in.
let lookback = 1d;
let minUsers = 15;      // <-- tune to the size of the tenant
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "50126"                 // invalid username or password
| summarize Attempts       = count(),
            UniqueAccounts = dcount(UserPrincipalName),
            Accounts       = make_set(UserPrincipalName, 50),
            Apps           = make_set(AppDisplayName, 10),
            Countries      = make_set(Location, 10),
            First          = min(TimeGenerated),
            Last           = max(TimeGenerated)
          by IPAddress, AutonomousSystemNumber
| where UniqueAccounts >= minUsers
// Few attempts per account confirms spraying rather than brute force:
| extend AttemptsPerAccount = round(todouble(Attempts) / todouble(UniqueAccounts), 2)
| where AttemptsPerAccount <= 3
| order by UniqueAccounts desc
```

### The most important follow-up question: did anything succeed?

<!-- query
platform: sentinel
name: Successful sign-in from an IP address that is spraying passwords
technique: T1110.003
severity: High
tactics: [CredentialAccess, InitialAccess]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
// Same source IP, but now the successful sign-ins. This is the point at which
// the Entra detection Password spray would first fire - and then only with P2.
let lookback = 1d;
let sprayIPs =
    SigninLogs
    | where TimeGenerated > ago(lookback)
    | where ResultType == "50126"
    | summarize UniqueAccounts = dcount(UserPrincipalName) by IPAddress
    | where UniqueAccounts >= 15
    | project IPAddress;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"                     // successful
| where IPAddress in (sprayIPs)
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AppDisplayName,
          ClientAppUsed, AuthenticationRequirement, ConditionalAccessStatus,
          RiskLevelDuringSignIn, UserAgent
| order by TimeGenerated desc
```

`ConditionalAccessStatus` and `AuthenticationRequirement` are not there for
decoration: a successful sign-in with `singleFactorAuthentication` from a spray
IP is the combination that measures 004 and 006 together ought to prevent.

### Include the non-interactive stream as well

Legacy protocols and clients that work with a token land in
`AADNonInteractiveUserSignInLogs`. Note: the Microsoft documentation describes
`ResultType` in that table as *"Success or Failure"*, whereas in `SigninLogs`
it is documented as the five- to six-digit error code. **Which of the two the
table contains in practice is not verified** — check that once in your own
workspace before filtering on the error code.

<!-- query
platform: sentinel
name: Password spray source across interactive and non-interactive sign-ins
technique: T1110.003
severity: Medium
tactics: [CredentialAccess]
interval: PT1H
lookback: P1D
parameters: []
deployable: true
-->
```kql
union SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(1d)
| where ResultType == "50126"
| summarize UniqueAccounts = dcount(UserPrincipalName) by IPAddress, Type
| where UniqueAccounts >= 15
```

## KQL — Defender XDR advanced hunting (EntraIdSignInEvents)

<!-- query
platform: defender-xdr
name: Password spray pattern from a single source address
technique: T1110.003
severity: Medium
tactics: [CredentialAccess]
interval: PT1H
lookback: P1D
parameters: []
deployable: false
-->
```kql
// Same logic, different table. ErrorCode is an int here, not a string.
let lookback = 1d;
EntraIdSignInEvents
| where Timestamp > ago(lookback)
| where ErrorCode == 50126
| summarize Attempts       = count(),
            UniqueAccounts = dcount(AccountUpn),
            Accounts       = make_set(AccountUpn, 50),
            Countries      = make_set(Country, 10),
            First          = min(Timestamp),
            Last           = max(Timestamp)
          by IPAddress, Application
| where UniqueAccounts >= 15
| extend AttemptsPerAccount = round(todouble(Attempts) / todouble(UniqueAccounts), 2)
| where AttemptsPerAccount <= 3
| order by UniqueAccounts desc
```

## KQL — making the Entra detection visible (Sentinel)

If you have P2, use `AADUserRiskEvents` to retrieve the detection and correlate
it with the rule above.

<!-- query
platform: sentinel
name: Identity Protection password spray risk detection
technique: T1110.003
severity: High
tactics: [CredentialAccess]
interval: PT1H
lookback: P7D
parameters: []
deployable: true
-->
```kql
AADUserRiskEvents
| where TimeGenerated > ago(7d)
| where RiskEventType == "passwordSpray"      // exact riskEventType from the Graph documentation
| project TimeGenerated, ActivityDateTime, UserPrincipalName, IpAddress, Location,
          RiskLevel, RiskState, RiskDetail, DetectionTimingType, Source, CorrelationId
| order by TimeGenerated desc
```

## Why this matters for BEC

In joint advisory **AA24-290A** (16 October 2024), the FBI, CISA, NSA, CSE, AFP
and ASD's ACSC describe how Iranian actors have since October 2023 used brute
force *"such as password spraying"* [T1110.003] and MFA push bombing [T1621] to
take over accounts in order to gain access to **Microsoft 365 and Azure**
[T1078.004], and then resell that access. That is exactly the chain the
advisory describes in the Credential Access and Initial Access phases: in BEC a
discovered password is not a goal but a boarding pass.
