# T1078.004 — Valid Accounts: Cloud Accounts

| | |
|---|---|
| **MITRE tactic** | Initial Access (classification used by the advisory). MITRE itself lists four tactics for this sub-technique: Stealth, Persistence, Privilege Escalation and Initial Access. |
| **Advisory measures** | 006 — Conditional access policy (priority High)<br>007 — Monitoring of suspicious sign-in attempts (priority High) |
| **Related techniques** | [T1110.003](T1110.003-password-spraying.md) and [T1539](T1539-steal-web-session-cookie.md) — where the valid access comes from |
| **Status of this detection** | KQL not executed against a production tenant — see [test status](../teststatus.md) |

## Recommendation

> ### `SENTINEL-RULE` — build your own analytic rule here
>
> No default alert policy for sign-ins exists at all: the complete overview of
> alert policies in the Defender portal is about mail, files, forms and
> administrative actions, not about sign-ins. The detection the advisory asks
> for under measure 007 sits entirely in Microsoft Entra ID Protection, and the
> detections that actually matter — *Atypical travel*, *Malicious IP address*,
> *Unfamiliar sign-in properties*, *Verified threat actor IP* — without
> exception require **Microsoft Entra ID P2**. Without P2 you get
> `Additional risk detected` without any details, and there is nothing you can
> do with that. You already have the sign-in logs themselves with P1; that is
> what you build the rules on. If you do have P2, also enable a risk-based
> Conditional Access policy — that is not a detection but the block that
> measure 006 intends.

## Is there a Defender alert for this?

**No, no alert policy. Entra ID Protection does cover it, and that is premium.**

The relevant sign-in risk detections, with the licence level as Microsoft
documents it per detection:

| Risk detection | `riskEventType` | Type | Licensing |
|---|---|---|---|
| `Anonymous IP address` | `anonymizedIPAddress` | Real-time | **Entra ID Free or P1** |
| `Microsoft Entra threat intelligence (sign-in)` | `investigationsThreatIntelligence` | Real-time or offline | **Entra ID Free or P1** |
| `Atypical travel` | `unlikelyTravel` | Offline | **Entra ID P2** |
| `Malicious IP address` | `maliciousIPAddress` | Offline | **Entra ID P2** |
| `Unfamiliar sign-in properties` | `unfamiliarFeatures` | Real-time | **Entra ID P2** |
| `Verified threat actor IP` | `nationStateIP` | Real-time | **Entra ID P2** |
| `Suspicious browser` | `suspiciousBrowser` | Offline | **Entra ID P2** |
| `Impossible travel` | `mcasImpossibleTravel` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, or **M365 E5 with EMS E5** |
| `New country` | `newCountry` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, or **M365 E5 with EMS E5** |
| `Activity from anonymous IP address` | `riskyIPAddress` | Offline | **Entra ID P2 + standalone Defender for Cloud Apps**, or **M365 E5 with EMS E5** |
| `Leaked credentials` | `leakedCredentials` | Offline | **Entra ID Free or P1** (requires password hash synchronization for on-premises passwords) |

Source: https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks

Two remarks that matter in practice:

- **`Atypical travel` and `Impossible travel` are not the same thing.** The
  first is an Entra detection on sign-ins, the second comes from Defender for
  Cloud Apps and looks at *activities*. They have different licences and
  different false positives. Do not conflate them in a runbook.
- **These detections do not apply to failed or non-interactive sign-ins.**
  Microsoft: *"Impossible travel, activity from infrequent countries/regions,
  activity from anonymous IP addresses, and activity from suspicious IP
  addresses alerts don't apply on failed logins and non-interactive logins."*
  With token replay in particular, the sign-in is non-interactive.

**Retired, do not build on this any more.** The Defender for Cloud Apps
policies `Activity from anonymous IP addresses` and
`Activity from suspicious IP addresses` were turned off as legacy policies in
June 2025 and migrated to the dynamic model, under `Activity from a TOR IP
address` / `Anonymous proxy activity` and `Successful logon from a suspicious IP
address` / `Activity from a password-spray associated IP address` respectively.
The identically named Entra detection `Activity from anonymous IP address` does
still exist.
Source: https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

**Measure 006 is a licensing fact, not an open question.** Conditional Access
requires **Microsoft Entra ID P1**; Microsoft 365 Business Premium includes it
too. Risk-based Conditional Access (sign-in risk and user risk) requires
**Entra ID P2**. Without P2 you can carry out the first three points of the
effective approach in the advisory (enforce MFA, block countries, device
compliance) but not the fourth (risk-based blocking).
Source: https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview

## Required data source

| Platform | Table | What needs to be onboarded |
|---|---|---|
| Microsoft Sentinel | `SigninLogs`, `AADNonInteractiveUserSignInLogs` | Data connector **Microsoft Entra ID**. Microsoft: *"A Microsoft Entra ID P1 or P2 license is required to ingest sign-in logs into Microsoft Sentinel."* |
| Microsoft Sentinel | `AADUserRiskEvents`, `AADRiskyUsers` | Same connector (log types *User risk events* and *Risky users*). Detection details require P2. |
| Microsoft Sentinel | `AuditLogs` | Same connector. Needed to see what the account did in the directory after the sign-in. |
| Microsoft Sentinel | `OfficeActivity` | Data connector **Microsoft 365** (Exchange workload). Requires an enabled Unified Audit Log — **measure 012**. |
| Defender XDR advanced hunting | `EntraIdSignInEvents` | **Entra ID P2**. Replaces `AADSignInEventsBeta` as of **19 October 2026**. |
| Defender XDR advanced hunting | `CloudAppEvents` | Defender for Cloud Apps connected (*Settings > Cloud apps > App connectors*, with *Microsoft 365 activities* enabled). Measure 012 applies here as well for the Exchange activities. |

One table you should **not** use here: `IdentityLogonEvents` contains
authentications from on-premises Active Directory (Defender for Identity) plus
the Entra sign-ins that Defender for Cloud Apps sees — and Microsoft notes that
these are *"specifically interactive sign-ins and authentication activities
using ActiveSync and other legacy protocols"*. Non-interactive sign-ins are
missing. For cloud sign-ins, `EntraIdSignInEvents` or `SigninLogs` is the right
source.

## KQL — Sentinel: successful sign-in with risk that was not blocked

```kql
// The core of measures 006 + 007 combined: Entra saw risk, and the sign-in
// succeeded anyway. That is either a gap in the Conditional Access policy, or a
// policy in report-only. Both are findings.
let lookback = 7d;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"
| where RiskLevelDuringSignIn in ("medium", "high")   // 'hidden' = no P2, leave that out
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AutonomousSystemNumber,
          AppDisplayName, ClientAppUsed, UserAgent,
          RiskLevelDuringSignIn, RiskEventTypes_V2, RiskState, RiskDetail,
          AuthenticationRequirement, ConditionalAccessStatus, SessionId
| order by TimeGenerated desc
```

`RiskLevelDuringSignIn` has the value `hidden`, and according to Microsoft that
means the user or the sign-in was not covered by ID Protection — so no P2. If
you only see `hidden`, there is nothing wrong with your query; there is no
licence.

## KQL — Sentinel: new country for this user (works without P2)

```kql
// Home-grown alternative to 'New country', which requires P2 + Defender for Cloud Apps.
// A baseline of 30 days, and then everything outside it. Deliberately on
// country and not on city: geolocation at city level is too unreliable to build an
// alert on.
let lookback     = 1d;
let baselineFrom = 31d;
let baseline     =
    SigninLogs
    | where TimeGenerated between (ago(baselineFrom) .. ago(lookback))
    | where ResultType == "0"
    | summarize KnownCountries = make_set(Location, 50) by UserPrincipalName;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"
| join kind=leftouter baseline on UserPrincipalName
| where isnotempty(Location)
| where isempty(KnownCountries) or not(set_has_element(KnownCountries, Location))
| project TimeGenerated, UserPrincipalName, Location, IPAddress, AutonomousSystemNumber,
          AppDisplayName, ClientAppUsed, AuthenticationRequirement,
          ConditionalAccessStatus, KnownCountries
| order by TimeGenerated desc
```

Exclude holiday periods and known travellers with a watchlist; otherwise this
rule is unusable in September.

## KQL — Sentinel: reading out the risk detections themselves

```kql
// All ID Protection detections in one list, including the detections that without P2
// arrive as 'Additional risk detected' (riskEventType 'generic').
AADUserRiskEvents
| where TimeGenerated > ago(30d)
| project TimeGenerated, ActivityDateTime, UserPrincipalName, RiskEventType,
          RiskLevel, RiskState, RiskDetail, DetectionTimingType, Activity,
          IpAddress, Location, Source, TokenIssuerType, CorrelationId
| order by TimeGenerated desc
```

```kql
// And the follow-up question that really matters in a BEC investigation: did
// anything happen in the mailbox after the risky sign-in? OfficeActivity requires
// measure 012 (UAL enabled).
let risk =
    AADUserRiskEvents
    | where TimeGenerated > ago(7d)
    | where RiskLevel in ("medium", "high")
    | project RiskAt = TimeGenerated, UserPrincipalName, RiskEventType, IpAddress;
OfficeActivity
| where TimeGenerated > ago(7d)
| where Operation in~ ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules",
                       "Add-MailboxPermission", "Set-Mailbox")
| join kind=inner risk on $left.UserId == $right.UserPrincipalName
| where TimeGenerated between (RiskAt .. RiskAt + 24h)
| project TimeGenerated, RiskAt, UserId, RiskEventType, Operation, ClientIP, Parameters
| order by TimeGenerated desc
```

## KQL — Defender XDR advanced hunting (EntraIdSignInEvents)

```kql
// Successful sign-in with a risk level during the sign-in. The scale is
// numeric here: 0 (not set), 1 (none), 10 (low), 50 (medium), 100 (high).
EntraIdSignInEvents
| where Timestamp > ago(7d)
| where ErrorCode == 0
| where RiskLevelDuringSignIn >= 50            // medium and high
| project Timestamp, AccountUpn, AccountObjectId, IPAddress, Country, City,
          Application, ClientAppUsed, UserAgent, RiskLevelDuringSignIn,
          RiskEventTypes, RiskState, AuthenticationRequirement,
          ConditionalAccessStatus, IsCompliant, IsManaged, SessionId
| order by Timestamp desc
```

`IsCompliant` and `IsManaged` are in the output because measure 006 explicitly
asks for them: a successful risky sign-in from an unmanaged device is a
different story from the same sign-in from a compliant laptop.

## Why this matters for BEC

In BEC a valid account is not an intermediate step but the whole objective:
nothing is installed, nothing is exploited, and so there is no malware to find
either. In advisory **AA24-290A** (16 October 2024), the FBI, CISA, NSA, CSE,
AFP and ASD's ACSC describe how actors use *"valid user and group email
accounts"* [T1078] to gain access to **Microsoft 365 and Azure** [T1078.004],
and then sell that access on criminal forums to parties who take it further.
Microsoft has a dedicated incident category for it in Defender XDR: at high
confidence *(attack disruption)* is appended to the title, with the
documentation giving as its example, verbatim, *"BEC financial fraud attack
launched from a compromised account (attack disruption)"*.
