# T1110.003 — Password Spraying

| | |
|---|---|
| **MITRE-tactiek** | Credential Access |
| **Whitepaper-maatregelen** | 004 — Phishing-resistente multifactorauthenticatie (prioriteit Hoog)<br>005 — Microsoft Defender for Office 365 (prioriteit Midden) |
| **Verwante technieken** | [T1621](T1621-mfa-request-generation.md) — wat er ná een geslaagde spray gebeurt<br>[T1078.004](T1078.004-cloud-accounts.md) — het gebruik van het gevonden wachtwoord |
| **Status van deze detectie** | KQL niet uitgevoerd tegen een productie-tenant — zie [TESTING.md](../TESTING.md) |

## Aanbeveling

> ### `SENTINEL-RULE` — bouw hier een eigen analytic rule
>
> Microsoft Entra ID Protection heeft een detectie die letterlijk **Password
> spray** heet, maar die is op twee manieren ongeschikt als enige dekking. Ze
> vereist Microsoft Entra ID P2 — zonder P2 zie je alleen *Additional risk
> detected* zonder details — en ze vuurt volgens Microsoft **pas nadat de
> aanvaller een wachtwoord succesvol heeft gevalideerd**: mislukte
> spray-pogingen tegen je gebruikers leveren geen detectie op. Daarmee is het
> geen vroegsignaal maar een compromis-melding. Het patroon dat je wél op tijd
> ziet — één bron, veel accounts, één wachtwoordpoging per account — bouw je
> zelf op de sign-in logs. Heb je P2, zet de Entra-detectie er dan als vangnet
> naast.

## Is er een Defender-alert voor?

**Deels, en alleen premium.** Er bestaat geen standaard alert policy voor
aanmeldingen: de policies in het Defender-portaal gaan over mail, bestanden en
beheerhandelingen, niet over sign-ins. De dekking zit in Entra ID Protection en
Defender for Cloud Apps.

| | |
|---|---|
| **Risk detection** | `Password spray` (sign-in risk, `riskEventType` = `passwordSpray`) |
| **Detectietype** | Real-time of offline |
| **Licentie** | **Microsoft Entra ID P2** |
| **Standaard severity** | Risk detections hebben een *risk level* (low/medium/high) in plaats van een alert-severity. Het vaste risk level van deze detectie is **niet publiek gedocumenteerd**. |
| **Beperking (belangrijk)** | Microsoft: *"The risk detection is only triggered when an attacker successfully validates a user's password. Unsuccessful spray attempts against your users don't generate a detection."* |
| **Zonder P2** | `Additional risk detected` — Free of P1, zonder detectiedetails |
| **Bron** | https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks |

| | |
|---|---|
| **Detectie** | Defender for Cloud Apps, `Multiple failed login attempts` |
| **Licentie** | Microsoft Defender for Cloud Apps (standalone, of M365 E5 met EMS E5) |
| **Wat het is** | Vuurt op meerdere mislukte aanmeldingen in één sessie ten opzichte van de aangeleerde baseline. Werkt per gebruiker, niet per bron-IP — een spray die één poging per account doet valt daar meestal buiten. |

**Vervallen, niet meer op bouwen.** De Defender for Cloud Apps-policy
`Activity from suspicious IP addresses` — de policy die password-spray-IP's
oppikte — is per juni 2025 als legacy policy uitgezet en volgens Microsoft
gemigreerd naar het dynamische model onder de namen `Successful logon from a
suspicious IP address` en `Activity from a password-spray associated IP address`.
Zie https://learn.microsoft.com/en-us/defender-cloud-apps/anomaly-detection-policy

**Wat níet je cloud-sign-ins dekt.** Microsoft Defender for Identity heeft
`Suspected Brute Force attack (Kerberos, NTLM)`, en de omschrijving noemt
password spray expliciet. Die detectie draait op sensoren op je domain
controllers en gaat over on-premises Active Directory, niet over aanmeldingen op
Microsoft 365. Reken hem niet mee als dekking voor deze techniek.

## Benodigde databron

| Platform | Tabel | Wat er onboard moet zijn |
|---|---|---|
| Microsoft Sentinel | `SigninLogs`, `AADNonInteractiveUserSignInLogs` | Data connector **Microsoft Entra ID**. Microsoft: *"A Microsoft Entra ID P1 or P2 license is required to ingest sign-in logs into Microsoft Sentinel."* |
| Microsoft Sentinel | `AADUserRiskEvents` | Zelfde connector (log type *User risk events*). Detectiedetails vereisen Entra ID P2. |
| Defender XDR advanced hunting | `EntraIdSignInEvents` | **Entra ID P2** vereist om deze tabel te vullen en te lezen. |

**Let op de tabelmigratie.** `AADSignInEventsBeta` wordt op **19 oktober 2026**
afgeschaft en vervangen door `EntraIdSignInEvents`; die laatste is nu al
beschikbaar en bestaande queries worden automatisch gemigreerd. Schrijf nieuwe
detecties op `EntraIdSignInEvents`.

Niet afhankelijk van maatregel 012 (UAL) — sign-in logs komen uit Entra ID, niet
uit de Unified Audit Log.

## KQL — Sentinel (SigninLogs)

```kql
// Spray-patroon: één bron raakt veel verschillende accounts met steeds dezelfde
// fout 50126 (InvalidUserNameOrPassword). Er wordt bewust NIET op het aantal
// pogingen per account gefilterd - dat is juist het verschil met brute force:
// bij spraying is dat er één of twee, waardoor smart lockout niet aanslaat.
let lookback = 1d;
let minGebruikers = 15;      // <-- afstemmen op de omvang van de tenant
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "50126"                 // invalid username or password
| summarize Pogingen        = count(),
            UniekeAccounts  = dcount(UserPrincipalName),
            Accounts        = make_set(UserPrincipalName, 50),
            Apps            = make_set(AppDisplayName, 10),
            Landen          = make_set(Location, 10),
            Eerste          = min(TimeGenerated),
            Laatste         = max(TimeGenerated)
          by IPAddress, AutonomousSystemNumber
| where UniekeAccounts >= minGebruikers
// Weinig pogingen per account bevestigt spraying in plaats van brute force:
| extend PogingenPerAccount = round(todouble(Pogingen) / todouble(UniekeAccounts), 2)
| where PogingenPerAccount <= 3
| order by UniekeAccounts desc
```

### De belangrijkste vervolgvraag: is er iets geslaagd?

```kql
// Zelfde bron-IP, maar nu de geslaagde aanmeldingen. Dit is het moment waarop
// de Entra-detectie Password spray pas zou vuren - en dan alleen met P2.
let lookback = 1d;
let sprayIPs =
    SigninLogs
    | where TimeGenerated > ago(lookback)
    | where ResultType == "50126"
    | summarize UniekeAccounts = dcount(UserPrincipalName) by IPAddress
    | where UniekeAccounts >= 15
    | project IPAddress;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType == "0"                     // geslaagd
| where IPAddress in (sprayIPs)
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AppDisplayName,
          ClientAppUsed, AuthenticationRequirement, ConditionalAccessStatus,
          RiskLevelDuringSignIn, UserAgent
| order by TimeGenerated desc
```

`ConditionalAccessStatus` en `AuthenticationRequirement` staan er niet voor de
sier: een geslaagde aanmelding met `singleFactorAuthentication` vanaf een
spray-IP is de combinatie die maatregel 004 en 006 samen zouden moeten
voorkomen.

### Ook de niet-interactieve stroom meenemen

Legacy-protocollen en clients die met een token werken landen in
`AADNonInteractiveUserSignInLogs`. Let op: de Microsoft-documentatie beschrijft
`ResultType` in die tabel als *"Success or Failure"*, terwijl hij in `SigninLogs`
gedocumenteerd staat als de vijf- tot zescijferige foutcode. **Welke van de twee
de tabel in de praktijk bevat is niet geverifieerd** — controleer dat één keer in
je eigen workspace voordat je op de foutcode filtert.

```kql
union SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(1d)
| where ResultType == "50126"
| summarize UniekeAccounts = dcount(UserPrincipalName) by IPAddress, Type
| where UniekeAccounts >= 15
```

## KQL — Defender XDR advanced hunting (EntraIdSignInEvents)

```kql
// Zelfde logica, andere tabel. ErrorCode is hier een int, geen string.
let lookback = 1d;
EntraIdSignInEvents
| where Timestamp > ago(lookback)
| where ErrorCode == 50126
| summarize Pogingen       = count(),
            UniekeAccounts = dcount(AccountUpn),
            Accounts       = make_set(AccountUpn, 50),
            Landen         = make_set(Country, 10),
            Eerste         = min(Timestamp),
            Laatste        = max(Timestamp)
          by IPAddress, Application
| where UniekeAccounts >= 15
| extend PogingenPerAccount = round(todouble(Pogingen) / todouble(UniekeAccounts), 2)
| where PogingenPerAccount <= 3
| order by UniekeAccounts desc
```

## KQL — de Entra-detectie zichtbaar maken (Sentinel)

Heb je P2, gebruik `AADUserRiskEvents` dan om de detectie op te halen en te
correleren met de rule hierboven.

```kql
AADUserRiskEvents
| where TimeGenerated > ago(7d)
| where RiskEventType == "passwordSpray"      // exacte riskEventType uit de Graph-documentatie
| project TimeGenerated, ActivityDateTime, UserPrincipalName, IpAddress, Location,
          RiskLevel, RiskState, RiskDetail, DetectionTimingType, Source, CorrelationId
| order by TimeGenerated desc
```

## Waarom dit BEC is

FBI, CISA, NSA, CSE, AFP en ASD's ACSC beschrijven in joint advisory
**AA24-290A** (16 oktober 2024) hoe Iraanse actoren sinds oktober 2023 met brute
force *"such as password spraying"* [T1110.003] en MFA push bombing [T1621]
accounts overnemen om toegang te krijgen tot **Microsoft 365 en Azure**
[T1078.004], en die toegang vervolgens doorverkopen. Dat is exact de keten die
het advies in de fasen Credential Access en Initial Access beschrijft: een
gevonden wachtwoord is bij BEC geen doel maar een instapkaart.
